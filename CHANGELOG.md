## [0.9.0] - 2026-08-07

### Added

- **Stay signed in on every device at once.** Logging in on your phone no longer signs your desktop out, **Settings** lists the devices you are signed in on and signs any of them out, and a sign-in you stop using eventually lapses on its own.

- **A throttled AI node parks the run instead of failing it.** When the provider cuts the agent off, the run waits in Human Feedback showing what the provider said, and **Resume** picks the same conversation back up once the limit lifts.

- **Start a work item from a branch other than the default.** A **Base branch** field sets the branch an item's runs start from and open their pull requests against; a branch that is missing fails the run rather than quietly falling back.

- **The repository's custom `.env` is shown to you when you open it, instead of a row of dots.** Editing it is an edit rather than a retype, clearing the field removes the stored value, and coding agents are still refused the plaintext.

- **Name a work item's branch yourself.** A **Branch name** field makes every run of that item use the name you give it instead of a generated one, and a run whose branch is already in use parks for you rather than starting on top of existing work.

### Changed

- **A coding agent reaching for something meant for you is refused rather than crashing the request.**

- **When an ILD tool fails, the agent is told why instead of only that something went wrong.**

- **The repository's preview `.env` now overrides a service's own `env`, instead of losing to it.**

### Fixed

- **The ILD tools work inside a worktree preview of ILD itself, where they were calling the wrong instance.**

- **arm64 images are built on native arm64 runners instead of under QEMU emulation.**

## [0.8.0] - 2026-08-02

### Added

- **Update example loop templates.** Refreshes the Q&A example and adds the DevTeam template to the example templates.

- **ILD has a favicon.** The tab, the bookmark and the pinned window now carry its flame mark, where before they carried the browser's blank default — the page pointed at an icon file that was never shipped.

- **The Files tab draws image files instead of dead-ending on "Binary file — preview not available."** PNG, JPEG, GIF, WebP, BMP, ICO and AVIF render in the viewer, scaled to fit; anything larger than 4 MiB still shows the binary message. SVG keeps rendering as source, because drawing untrusted markup would bring any script in it along.

- **An AI node's session name can now interpolate a loop variable, giving one session per iteration instead of one per loop.** Write `{{Var.current_ticket}}` into the name and each distinct value gets its own session, resumed whenever that value recurs. Only `{{Var.*}}` is accepted; an unset or empty variable fails the node rather than silently collapsing every iteration into one conversation.

## [0.7.0] - 2026-08-01

### Added

- **A stop no longer costs a run its in-flight step.** ILD had no SIGTERM handling at all, so `docker compose stop`, a Kubernetes rollout or a GitOps image bump killed the whole process tree with the agent CLIs mid-step — leaving the run row `Running`, its node `Running`, and no session snapshot (the adapter only writes one on a clean exit), so the next start re-drove that node cold and repeated minutes of agent work in a worktree that already held the half-finished result. A stop is now treated as a halt ILD inflicted on itself rather than as a crash. When the host announces it is stopping, one flag is raised that every component reads at the same moment — `ApplicationStopping` fires once, before any hosted service stops, which the components' own stopping tokens do not — and from that instant no new run driver launches and no new work item is claimed, while heartbeats keep running so live runs hold the claims they already have. The drain then parks each run it is driving on an **AI** node exactly the way the Halt button does — `WaitingHuman`, halted, keeping `CurrentNodeId` and the captured agent session — but stamped as a shutdown halt, with no "human input needed" reason and **no work-item transition at all**: leaving the item `Running` on the server is what lets the next start recognise the run as still ours. A run on a Cmd or Condition node is cancelled and left `Running` for ordinary crash recovery, because that step is cheap to redo and not worth a park somebody may have to clear. The drain then waits for the driving loops to unwind, and the wait is the feature rather than a courtesy: the park is written before the agent process is killed, but the interrupted-node bookkeeping happens as the loop unwinds, so a process that exited first would leave precisely the half-written state this removes. On the next start those runs resume automatically through the halt path against the same agent session with `"Continue where you left off."`, honouring each run's `RecoveryPolicy` — `Cancel` and `NeedsReview` are an operator's statement about restarts, and a tidy restart is still a restart — and its worktree health. Three paths look for them, because one is not enough: startup recovery, the remote work-item startup reconciler (the live path when `ILD_WORKITEM_SERVER_URL` is set), and the stuck-run watchdog as a backstop, since startup reconciliation is skipped wholesale when the work-item server is unreachable — exactly what happens when one deploy rolls both containers — and swallows its own failures, so without it the tidiest possible shutdown could park a run forever. A halt a **human** pressed is never auto-resumed by any of the three: the halt now records _why_ it happened rather than the resume paths guessing from a row shape the two share, and the reason is null for every row written before this, so those read as human halts and are left alone. The drain's budget is `ILD_SHUTDOWN_DRAIN_SECONDS` (default 20s, falling back to the default for anything malformed or non-positive — `0` would silently restore the hard kill), and the host's own shutdown timeout is derived from it at drain + 5s so the host cannot abandon the unwinding it just asked for. One budget lives outside ILD: compose defaults `stop_grace_period` to 10s, which is _shorter_ than the drain, so `docker-compose.yml` now sets 30s on the `ild` service; Kubernetes' 30s pod default already fits. See [ADR-0017](docs/adr/0017-shutdown-halts-the-in-flight-ai-node.md) for why the in-flight node is halted rather than allowed to finish, [Configuration](docs/configuration.md#graceful-shutdown) for the sequence and resume rules, and [Deployment](docs/deployment.md#shutdown-and-run-draining) for the grace-period requirement.

- **Stop a chat reply mid-flight.** The chat bubble shows a red stop square to the left of **Send** for exactly as long as a turn is in progress, cancelling it over the new `POST /api/v1/chat/{id}/interrupt`. The cancel primitive already existed — it was reachable only by sending another message or deleting the chat, so there was no way to just make the agent stop. The endpoint checks ownership before cancelling, exactly as the per-chat delete does, and the button does not clear the busy state itself: the server persists the partial reply and announces it, so an interrupted turn ends through the same hub events as one that finished on its own and the transcript keeps what the agent had produced (flagged `interrupted`). A stop that loses the race to the turn finishing is a no-op rather than an error.

### Changed

- **The loop authoring guide a chat agent is given in the Loop Editor now covers the rules that make a hand-written loop fail.** It described the document shape and little else, so an agent could compose a well-formed loop that the save rejected outright, or one that saved and then ran wrong. The save-time rules are now stated: an edge whose `sourceNodeId` or `targetNodeId` names no node in the same document is dropped **silently**, with no error and no validation failure, so a structural edit has to be read back and checked; every node must be reachable from `Start` or the whole save is rejected, which is the rule a hand-written document fails most often; an AI node's `matchRules` and its Custom edges must correspond both ways; and `useSession` requires a non-empty `sessionPlaceholder`, so a fork-only configuration is refused. Field semantics come with them — `toolAllowlist` has exactly four keys (`read`, `write`, `execute`, `ild`), honoured only by the opencode/pi/claude-code providers, and an empty, omitted or fully-filtered list means the **provider defaults** rather than "no tools", which the field cannot express at all; an unset or non-GUID `aiProviderId` falls back to the default provider, while a GUID that no longer exists fails the run outright, and there is no endpoint an agent can list providers from. Routing is now described against what it actually matches: AI `matchRules` take the **last** match against the entire node output, Condition cases the **first** against that case's own rendered subject, both case-insensitively and with neither `Multiline` nor `Singleline` set — so `^` and `$` bind to the whole string rather than to a line, which is why the form to recommend is `(?m)^TO_REVIEW$` and why a bare `^TO_REVIEW$` never matches an agent that explains itself before the verdict. Only AI `matchRules` are probed at save for zero-width and catastrophically slow patterns; a zero-width Condition case compiles, saves cleanly and then matches everything, and as the first case it wins forever, so no later case or `defaultEdge` is ever reached. Four authoring practices are added, the headline one being that an AI node re-renders and re-sends `config.prompt` on **every** visit, so the brief belongs in an upstream Prompt node rather than inlined where each pass around the loop pays for it again. Nothing about loop execution or the document format changes — this is only what the agent is told about them, and it is the same constant the new `get_loop_authoring_guide` tool below serves. See [ADR-0011](docs/adr/0011-context-aware-chat.md).

### Fixed

- **A preview start that fails partway no longer leaves the services it already launched running, and a service is no longer started while a service it references is down.** Both are the "every surface says healthy while the link between two services is dead" failure, reported as a `${PORT:alias}` cross-reference resolving to the previous run's port: this repository's own profile has `api` reach the WorkItem Server at `http://127.0.0.1:${PORT:workitem-server}`, and an `api` was seen polling a port from an earlier run for its whole lifetime — no scheduling, no claiming, no runs, and nothing wrong in `get_preview`. Resolution itself turned out to be sound; a whole-profile restart re-wires every cross-reference to the new run's ports, ephemeral ones included, and there are now regression tests that force a different port on the second start rather than hoping for one. What produced a process outliving its ports was the **start path**: the runtime a preview's services belong to was published only after the last health probe passed, so a failure anywhere before that — one unlaunchable service, a health check that never came good, a cancelled start — left every service launched ahead of it running and unreachable to every stop path there is. Those orphans kept the ports and the `${PORT:alias}` values that attempt had baked into them, held those ports against the next start, and went on appending to the same per-service log, where their output is indistinguishable from the current run's. A failed start now stops what it started, so a preview is either up or gone. The second half is the case no teardown can reach: starting **one** service whose `${PORT:alias}` names a service that is not running. Every alias in the profile is allocated up front — that is what makes per-service starts wire together at all — so the reference resolves to a real number nothing is listening on, and the service then reports healthy because its health check only asks about itself. That start is now refused, naming both services and which to start first, rather than succeeding into a broken link. A service restarted on its own still keeps its alias's existing allocation, which is what keeps a still-running referrer correct, and `suggestedPort` still pins a port across restarts for a stable URL — it is no longer the thing standing between a profile and a working cross-reference. See [Configuration](docs/configuration.md#ports-across-restarts).

- **A chat held on the Loop Editor page no longer pays for the loop authoring guide on every turn.** The Chat Context preamble — the ~7.7k-char guide included — was prepended to every user message, and a chat turn resumes the provider's agent session rather than replaying ILD's own transcript, so each turn left another verbatim copy in a history the earlier copies had never left. Ten turns meant ten copies; because an input context is re-read on every turn, the cost was quadratic in the turn count rather than linear, and on a measured ten-turn conversation ~90% of what the agent had been sent was duplicated preamble. The preamble is now split by what actually changes. The **per-turn** half is unchanged and still arrives every turn, because it is state: the open work item id, the active run's worktree path and its directory grant, and whether a Loop Editor is open at all. The **constant** half — the loop-editor brief and the authoring guide — is now a **Session Briefing**: delivered once into the agent session that will hold it, recorded against that session rather than as a "sent it once" flag, so a session that is rebound or forked is briefed afresh instead of silently going without; the re-brief lands on the turn after the rebind, since which session a turn binds is only known once the CLI reports it, and a turn that never reached an agent at all does not count as having briefed one. The guide is the only briefing today, but the mechanism is not specific to it, and a per-turn size budget in the tests fails the build if the next constant block is inlined into the preamble instead. Sending it once would be a poor trade on its own — guidance that far back in a long conversation is guidance the model may stop attending to — so the guide is also **pullable** now, by a new `get_loop_authoring_guide` tool (`ild_get_loop_authoring_guide` on the Pi surface, `GET /api/v1/agent/loop-authoring-guide`) that serves the same constant the chat pushes, and the thin per-turn pointer names it. That is what ADR-0011 already said this context should do — heavy content pulled on demand, only a thin pointer pushed — and the guide was the one thing still being pushed. The split does not alter the guide's content (which changed on its own account — see Changed above), and no configuration changes. See [ADR-0011](docs/adr/0011-context-aware-chat.md).

- **Placeholders no longer vanish from chat messages or from anything a prompt quotes.** Template rendering used to sit in the CLI adapter base, below every agent launch, so it ran on two things that are not templates. A chat turn was rendered against an empty run context: the Chat Context preamble teaches the placeholder grammar by quoting it, and a human asking about that grammar had their own question rewritten, so both the guide and the question reached the agent full of holes — and an agent that believes an emptied token can write that emptiness back into a live loop through the loop-edit tools. An AI node's prompt, meanwhile, was rendered twice: once by the node executor with the full run context, then again by the adapter with a weaker one, so a placeholder quoted inside substituted content — a work item description saying which loop variable to write, a variable value, a previous node's output, an earlier agent's explanation of the syntax — was eaten on the second pass. Rendering now belongs to the node executors alone, which is where the run context lives: **each template field is expanded exactly once, by the node that owns it; text a placeholder pulls in is never scanned again; the adapter layer passes the prompt through byte-for-byte.** The eight templated fields (the AI, Prompt, Human and PR prompts, the PR description and comment templates, and the Condition output and case subjects) expand exactly as before, and the placeholder syntax is unchanged. Two behaviour changes fall out of it: a chat message naming a file with a worktree-file placeholder is no longer replaced with that file's contents (an undocumented side channel — the agent already has the scratch directory as its cwd), and a steering note typed at halt→resume now reaches the agent verbatim, like any other message a human writes. See [ADR-0011](docs/adr/0011-context-aware-chat.md).

- **A preview no longer fails to build in a worktree the coding agent has already built in.** `error MSB3021: … Access to the path '…/bin/Debug/net10.0/…' is denied` and `error MSB3374: The last access/last write time on file … cannot be set` came from two users building in one tree: a file created `0755` by one clamps the inherited `g:ild-agents:rwx` ACL to an effective `r-x` for the other, and setting an explicit mtime through `utimensat` requires being the file's **owner**, which no mode or ACL scheme can grant. Any toolchain that rewrites an existing output tree can hit this; .NET just names it precisely. Running the preview as the same user the agent builds under removes the class of failure rather than working around it — a per-uid MSBuild `ArtifactsPath` would have treated the symptom, and only for .NET. A worktree previewed on an older build still holds mixed-ownership output and needs clearing once; [Troubleshooting](docs/troubleshooting.md) has the command.

- **A previewed app that reads ILD's own variables is now cleanly separated from the instance running it.** In practice that means previewing an ILD — this repository's profile does, and it inherited `ILD_AGENT_USER` from the outer instance, concluded uid isolation was on, and routed its own agent launches through `setpriv --reuid` without holding `CAP_SETUID`, dying with `setpriv: setresuid failed: Operation not permitted` when an interactive provider terminal was opened. It also shared the outer instance's private directory and, having inherited its connection strings, its live database — running background services against it for real. The three overrides this repository carried on its `api` service to work around that (`ILD_AGENT_USER: ""`, `ILD_ORCHESTRATOR_PRIVATE_ROOT`, `ILD_AGENT_SCRATCH_ROOT`) are removed, since the behaviour they bought is now how every preview works. Anyone on an older build will find them recorded in [Troubleshooting](docs/troubleshooting.md).

- **A work item that has not started can be moved back to Backlog from the board.** Dragging a card from **Ready** to **Backlog** — or using the keyboard move, or picking Backlog from the status dropdown — answered `400 {"error":"Transition not allowed"}` and snapped the card back. All three surfaces post to `POST /api/v1/workitems/{id}/transition`, whose target switch had arms for every status _except_ Backlog, so the move fell through to the catch-all rejection; the work-item server had been accepting the target all along, so nothing but the API layer was refusing. Backlog is now reachable from **WorkQueue**, **Ready** and **HumanFeedback**, which is the full reset for re-planning this document already describes, and it keeps a run's worktree and branch exactly as before. An item whose run is still alive (Running, or parked at a human gate) deliberately keeps the refusal rather than being quietly relabelled: the active work item set is derived from live runs, so a run left alive under a Backlog card would go on being heartbeated and holding a concurrency slot — the same hazard the move to **Done** guards against by ending the run first. Sending a _started_ item back to Backlog is unchanged and still belongs to **Abandon run** in the work item dialog, which stops the run first. A run that already failed or was cancelled does not block the move.

### Security

- **A Worktree Preview no longer runs as the orchestrator, and no longer inherits its environment.** The commands a preview runs come from the worktree's `ild.config.json` — a file the coding agent writes, and can trigger through the ILD MCP tools whenever it likes — so they now run as the lower-trust `agent` uid, with an environment ILD constructs rather than one .NET hands the child by copying ILD's own. Two categories were leaking into every previewed repository. **Secrets:** both database connection strings, `ILD_SECRET_KEY`, the bootstrap credentials, and the API tokens ILD uses to reach itself and the WorkItem Server all reached preview commands verbatim, so `command: "env > leak.txt"` plus a `start_preview` call read back the exact values the uid split exists to withhold from the agent — with a `"public": true` service on the wildcard preview host as a ready exfiltration channel. Your app never had to read those names to be a problem: your build and start commands ran with them in `env`, so one debug `printenv`, a crash reporter that captures the environment, or a script that forwards it was enough to carry them out. **ILD's own uid topology:** `ILD_AGENT_USER`, `ILD_AGENT_GROUP`, `ILD_AGENT_HOME`, `ILD_AGENT_SCRATCH_ROOT` and `ILD_ORCHESTRATOR_PRIVATE_ROOT` are not secret, but they describe the ILD process and are wrong for anything else — an app that reads them is pointed at ILD's own identity and private directories, including the git askpass helper handed to git as `GIT_ASKPASS` with a repository token in its environment. Stripping happens **before** a step's own environment is applied, so anything a repository sets deliberately — in its encrypted preview `.env` or a service's `env` block — still wins; what is removed is only ever what was inherited. What the preview itself writes — the npm cache, anything under `${STATE_DIR}` — moves to the shared scratch root so the agent uid can write it, while the install and service logs stay in ILD's private root because ILD still writes and reads those; and the npm global prefix follows the agent's home so `npm install -g` lands where the uid running it can write. The capability-drop helper that `ProcessRunner` and Cmd nodes share is deliberately untouched — a Cmd node may legitimately rely on the inherited environment, and folding the scrub in there would have changed both silently. **Upgrade note:** a service that used to come up on configuration nobody wrote down was reading ILD's, and now needs its own — a database connection string, most often. Note also what this does _not_ change, and what 0.5.0's per-repository `.env` entry below overstated: that `.env` is still injected into every preview process by design, and preview commands come from `ild.config.json`, which the coding agent writes — so its values remain readable to an agent-authored command, and belong scoped to the preview's own infrastructure rather than to production. See [Configuration](docs/configuration.md#giving-a-preview-its-own-configuration) and [ADR-0016](docs/adr/0016-preview-runs-as-the-agent.md), which also records what the change costs: preview state is now reachable by every run's agent through the shared group, and the shared credential store behind `$HOME` stays shared on purpose.

- Cleared all 12 Dependabot advisories. `react-router` 7 → 8.3.0 (GHSA-qwww-vcr4-c8h2), replacing the `react-router-dom` dependency: since v7 that package only re-exported `react-router` to ease the v6 upgrade, and v8 drops it, so imports now come from `react-router` directly. This also raises the React floor to 19.2.7, which v8 requires. The rest are build- and test-only: `jsdom` 29 → 30 (moves undici 7 → 8, clearing seven advisories), `vite-plus` 0.1 → 0.2 (lifts postcss to 8.5.25, GHSA-r28c-9q8g-f849), and an explicit `SQLitePCLRaw.bundle_e_sqlite3` 3.0.5 reference in `ILD.Tests` (GHSA-2m69-gcr7-jv3q, which has no fix under the old package id).

## [0.6.0] - 2026-07-30

### Added

- **Worktree previews are reachable through ILD's own port, on wildcard subdomains.** A preview binds its services to ports allocated at runtime inside the container, so the `http://<publicHost>:<port>` URL the Preview tab has always produced is unreachable the moment ILD sits behind an ingress or a container boundary — the URL was there, it just resolved to nothing. Setting the new `ILD_PREVIEW_PROXY_BASE` (e.g. `http://ild.localhost:8080`) makes ILD serve previews itself: `wi-<workItemId>.<base>` reaches the profile's `"public": true` service and `wi-<workItemId>-<serviceName>.<base>` reaches any one service by name, hyphens in the name included (the work item id is the digits right after `wi-`, so the split is unambiguous). Mark exactly one service `"public": true`: a profile with several has each advertised as `wi-<workItemId>-<serviceName>` instead, since the bare form names only one. Requests are forwarded with `X-Forwarded-Proto`/`-Host`/`-For`, redirect `Location` headers and `Set-Cookie` domains rewritten onto the preview hostname, and no response buffering, so streaming endpoints, every HTTP method, large bodies and WebSocket upgrades pass through. The base also declares the scheme browsers use — set it to `https://…` behind a TLS-terminating ingress, since ILD listens on plain HTTP and the incoming request cannot tell it how the browser arrived. The `Host` header is rewritten to the loopback target by default — host-checking dev servers reject the preview hostname outright — and a service that would rather see the browser-facing hostname opts out with the new `"rewriteHost": false` in `ild.config.json`. `publicUrl` in the Preview tab now follows an explicit precedence: an authored `publicUrl` template, then the proxy origin, then the historical direct URL; with the variable unset every URL is byte-for-byte what it was. Anything the proxy will not forward — an unknown work item, a preview nobody started, a crashed service — answers with one indistinguishable 404, so the response reveals nothing about ILD's internal state; the reason goes to the log instead. Two things are needed outside this repository before a browser can reach a preview in a cluster: wildcard DNS for `*.<base>` and a wildcard SAN on the ingress certificate. Note that neither is access control — the hostname travels in a client-supplied `Host` header — and **a running proxied preview is unauthenticated**, since the proxy must run ahead of authentication for a foreign app with no ILD session. Network access to ILD's port is the boundary; `ILD_PREVIEW_PROXY_BASE` remains the switch that turns the whole path off. See [ADR-0015](docs/adr/0015-wildcard-subdomain-preview-routing.md) for why subdomains rather than path prefixes, and [Deployment](docs/deployment.md#worktree-preview-proxy) for the security model and the per-framework hot-reload caveat (pages load; live reload needs its own configuration).

### Changed

- **Compose publishes only `8080`, and enables the preview proxy by default.** The `3100:3100` and `5100:5100` mappings existed to make previews reachable, and only ever worked for the two ports this repository's own preview profile happens to suggest — never for a second concurrent run, and never for another repository. Previews now go through `8080` via the preview proxy above, which compose points at `http://ild.localhost:8080` (browsers resolve `*.localhost` to loopback with no `/etc/hosts` entry). The ILD UI is unaffected on `http://localhost:8080`. **This does widen the default unauthenticated surface**, from two published ports that only ever served one repository's profile to every running preview for every repository, on the port operators actually publish. What bounds it is that nothing is served unless someone started that preview — every preview hostname with no running preview behind it is a flat 404 — so the exposure lasts as long as the preview does, and network access to ILD's port is the boundary. Set `ILD_PREVIEW_PROXY_BASE=` in your `.env` to turn it off.

### Fixed

- **The .NET test suite no longer depends on the environment that launched it.** `ILD.Tests` pins the [ADR-0014](docs/adr/0014-agent-uid-isolation.md) uid-isolation variables to their documented unit-test baseline before any test runs, so `dotnet test` behaves the same in CI as it does inside the running container as the `agent` uid — where the entrypoint has already exported them and 77 tests failed for reasons unrelated to the code under test. The ADR states the intent ("routing is a no-op unless `ILD_AGENT_USER` is set, so unit tests keep the pre-isolation behavior unchanged") and the tests are written to it, driving isolation through the explicit-parameter overloads; nothing enforced the "unless" half, so the guarantee only held where the variables happened to be absent. The two roots need opposite treatment: clearing `ILD_AGENT_SCRATCH_ROOT` suffices because its fallback is `TMPDIR`, but `ILD_ORCHESTRATOR_PRIVATE_ROOT` has to be redirected, since its fallback is the fixed `TMPDIR/ild-orchestrator-private` the entrypoint has already created `0700` under the orchestrator's uid. A guard test asserts the baseline, so a regression surfaces as one named failure instead of 77 scattered ones.

- **A PTY session no longer hangs teardown when the child refuses to die.** `PtyWebSocketBridge` drained the PTY→socket pump with an unbounded `await`. That await is only ever unblocked by the `pty.Kill()` immediately above it — the Unix PTY reader stream does not observe the cancellation token, as the surrounding comment already noted — and `Kill()`'s failure is deliberately swallowed. So whenever the kill did not take, teardown waited forever with the child still parked on its pty. The drain is now bounded the same way the socket drain below it already is; the `finally` block kills and disposes regardless, so giving up early costs nothing. Found inside the running container, where `dotnet test` stopped dead at 877/1018 with `InteractiveProviderSessionServiceTests.BridgesBytesBetweenWebSocketAndPty` never completing and a `/bin/cat` child still sleeping on `/dev/pts/1` — the same test passes in 102 ms in isolation, so the race only shows under load, which is why it never surfaced on CI's faster runners. The full suite now completes 1018/1018 in-container, both with the entrypoint's isolation variables ambient and with them stripped.

## [0.5.0] - 2026-07-26

### Added

- **Pull the run branch from origin, for a human and for the AI.** A WorkItem's Worktree could be pushed but never pulled, so commits landing on the run branch after the run started — a human fix, a review commit, another ILD instance — were unreachable: under [ADR-0014](docs/adr/0014-agent-uid-isolation.md) the agent uid can read neither the repository token nor the `GIT_ASKPASS` helper, so `git pull` inside the worktree can never authenticate. Both surfaces now go through one orchestrator-credentialed `PullBranchAsync`: a **Pull branch** button beside **Push branch** in the work item dialog (`POST /api/v1/workitems/{id}/pull-branch`), and a `pull_branch` MCP tool / `ild_pull_branch` Pi tool over `POST /api/v1/agent/workitems/{id}/pull-branch`. It fetches origin with the repository's credentials and rebases the branch onto **its own** remote counterpart (`origin/ild/wi-<id>-run-<runId>`); syncing onto the repository's default branch remains the Start node's job ([ADR-0006](docs/adr/0006-run-isolation-clean-origin-base.md)) and is deliberately not done here. Nothing about the credential crosses the uid boundary — the agent asks the orchestrator to pull, it never pulls itself. The result is a structured outcome the caller can act on rather than a bool: `Updated`, `AlreadyUpToDate`, `NoRemoteBranch` (never pushed — an explicit no-op, not an error), `DirtyWorktree` (refused, naming the uncommitted files; deliberately no auto-stash, which could swallow an agent's in-flight work), `Conflict` (naming the conflicted files) or `RebaseRefused` (git declined outright — nothing to resolve, just a reason). A rebase that cannot complete is now always `git rebase --abort`ed before returning — including when it is killed by cancellation, where the worktree outlives the run that owned it ([ADR-0008](docs/adr/0008-worktree-and-branch-per-run.md)) — so ILD no longer walks away from a half-rebased worktree on any path (the unwind is git's own, so it narrows the window rather than closing it absolutely). This also hardens the Start node's rebase onto the default branch.
- **GitHub Copilot AI provider** — a new `copilot` provider type backed by a `CopilotAdapter` that runs GitHub's `copilot` CLI headlessly (`copilot --allow-all-tools --no-color --add-dir <worktree> -p <prompt>`, the documented programmatic form) inside the run's worktree and captures its plain-text stdout as the node output. Like `claude-code` it is a CLI-auth managed agent: it installs on demand from the `@github/copilot` npm package onto `/data`, authenticates via the CLI's own `/login` (a GitHub Copilot subscription, credentials under `~/.copilot`), and needs no Base URL, API key, or model. The AI Provider page hides those fields and shows a Copilot-specific login note when the type is selected. Two intentional differences from the other CLI adapters: Copilot runs **single-turn** (its `-p` mode does not surface a resumable session id, so ILD cannot persist/restore sessions for it), and it always runs **with all tools allowed** (`--allow-all-tools` is required for headless use), so the per-node read/write/execute/ild allowlist is not applied to Copilot.
- **Smarter work-item tools for AI triage** — the agent listing now returns a compact, relationship-aware projection instead of every full body. `list_workitems` drops the full `description` for a single-line `descriptionPreview` and adds `priority`, `tags`, the dependency ids blocking each item (`blockedBy`/`blockedByCount`), the reverse-edge count of what it blocks (`blocksCount`), and an `actionable` flag (all dependencies Done). It also gains `priority`, `tags[]`, `orderBy` (updatedAt | createdAt | priority), and `actionableOnly` filters/sort. For backward compatibility an `includeDescription` flag re-adds the full body per row (off by default); the `blockedBy` id array is capped (50 ids/row) while `blockedByCount` stays exact. A new `get_backlog_summary` tool/endpoint aggregates counts by status and priority plus blocked-vs-actionable totals with no bodies, so an agent can orient over a large backlog before drilling in. `get_workitem` now also resolves reverse `blocks` edges and gates the (large) `conversation` behind an explicit `includeConversation` flag.
- **Retained chat history** — the chat bubble keeps every chat instead of holding one ephemeral session per user. Past chats are listed under **Start chat**, each auto-named from its first message and date-stamped; clicking one resumes its full transcript, and a chat can be deleted individually or all at once behind a confirmation. A chat now persists until you delete it: the hard-delete-on-end and the idle retention sweeper are gone. See [ADR-0013](docs/adr/0013-retained-chat-history.md).
- **Targeted loop-edit tools, and a review diff before every save.** The chat agent edits an open loop through scoped tools (`get_loop_node`, `edit_loop_node_field`, `set_loop_node_field`, `get_loop_file`, `edit_loop_file`) instead of re-serializing the whole document — which used to corrupt unrelated nodes and gave no acknowledgement. Each edit returns a synchronous `{ applied, matchCount, validationErrors }`, string replaces must match uniquely, and every result is re-validated before it lands: an edit that would produce an invalid template is rejected and the document left exactly as it was. On the human side, **Save** now opens a review modal showing the full JSON diff of everything pending — Save persists precisely the snapshot you reviewed (an AI push arriving mid-review cannot slip into it), Cancel aborts.
- **Word-level highlighting in diffs.** A changed line is no longer painted one solid tone, which on a long line says only "something in here moved". Both the loop editor's save-review diff and a work item's **Files** tab now render a changed line in two tiers: the whole line lightly, the words that actually differ from its counterpart strongly — the difference between unreadable and obvious when the line is a JSON-escaped prompt thousands of characters long. Bounded by per-pair and per-document caps, so a pair that is too large, too lopsided, or too dissimilar to be worth splitting falls back to today's whole-line shading and the view never stalls.
- **Per-repository custom `.env`, injected into preview processes.** A repository can carry a block of `.env` text that is supplied as environment variables to every preview process it runs — the install step and each service — so a preview that needs an API key or a database URL can have one without committing anything. Precedence is base defaults < repo custom `.env` < the per-service `env` in `ild.config`. It is stored encrypted at rest (the same AES-256-GCM path as provider API keys), masked on read like an API key, never written to a file in the worktree, and never returned through the agent API — so a coding agent cannot read it back. Editable from the Repositories page, and from a work item's **Preview** tab with a prominent warning that the value belongs to the repository and applies to every work item using it.
- **Per-provider Custom MCP servers.** An AI provider can carry its own MCP server map as JSON — e.g. an "OpenCode w/chrome" provider carrying `chrome-devtools` — merged into the generated agent config alongside ILD's own `ild` server, for every repository that provider runs in. Wired for `opencode` and `claude-code` (Pi has no MCP by design; Copilot is not MCP-wired in ILD) and edited from the AI Providers form. The reserved `ild` name cannot be clobbered, and malformed JSON is ignored rather than failing the run.
- **Per-work-item AI provider override** — a work item can redirect its AI nodes at a chosen provider in one of two modes: **Override default** swaps only the nodes that fell back to the configured default provider, leaving nodes pinned to a specific provider alone; **Override all** swaps every AI node. Set from the work item dialog's edit panel or when creating the item.
- Adding a repository auto-fills its name and default branch from the remote's advertised `HEAD` (`git ls-remote --symref`, honoring the same credentials as clone) when the clone URL loses focus. Both stay editable, and an unreachable remote degrades quietly to manual entry.
- Pi agents now receive `ild_get_loop_variables` and `ild_set_loop_variable` alongside the MCP tools, so a Pi node can read and write per-run loop variables like the other adapters.
- A **DevTeam** experimental loop template — a 25-node orchestrator/explorer/developer/QA/reviewer loop with an optional HIL-tag gate that inserts human approval before the PR is opened. It lives in `experimental-loops/`, so it is not seeded as a template.

### Changed

- **The Condition node is now an N-case switch.** Instead of one predicate routing to fixed `true`/`false` edges, a Condition node holds an ordered list of cases — each with its own `TextMatches` / `PrExists` / `HasTag` predicate and its own named edge — plus a default edge taken when nothing matches; the first matching case wins. Existing true/false conditions keep routing identically: a legacy config is read at runtime as a single case with a `false` default, and a startup migrator converts persisted ones to the switch shape. A resolved edge name that is blank now fails the node onto `OnFailure` with a reason rather than silently completing the run.
- **An AI node's match rules now route by the _last_ match in the output, not the first.** Agents narrate their reasoning, so a reviewer writing "I found no reason to reject, so: approve" tripped the `reject` rule and took the reject edge — the opposite of its verdict. Each rule now finds its own last occurrence and the rule matching furthest into the output routes, ties breaking on the longer match and then configured order; the closing verdict beats anything mentioned on the way there, and rule order no longer sets priority. Patterns are also checked when the template is saved — one that does not compile, or one that can match zero characters (`x*`, `\b`, `(?=…)`, which would otherwise outrank every genuine verdict) — is rejected while the author can still fix it. At runtime a malformed or catastrophically-backtracking rule is skipped under a 1s timeout instead of failing the node, so an existing config with one bad rule keeps routing as it did.
- The `[Ild: <label>]` marker prefixing each node's first live output is now bold cyan, so node hand-offs stand out from ordinary output in the live view.
- **`WITH_CHROME=1` now installs Chrome on arm64 as well as amd64.** Google [publishes google-chrome-stable for arm64 Linux](https://blog.google/chromium/bringing-chrome-to-arm64-linux-devices/), so the Dockerfile's `dpkg --print-architecture` = `amd64` guard — which silently produced a browser-less arm64 image — is replaced by an arch case that fetches the matching `.deb`. arm64 is a first-class published target (ADR-0012 ships both images amd64 + arm64), so an amd64-only Chrome was an inconsistency. The arm64 package installs the same `/opt/google/chrome/chrome` that Puppeteer's `--channel stable` resolves, so `chrome-devtools-mcp` needs no configuration change. Architectures Google does not publish (e.g. armhf) still skip the install with a message rather than failing the build, and the `.devcontainer` Chrome feature selects its `.deb` the same way. CI's `ild-arm64` job (`image-extra.yml`, linux/arm64 under QEMU with `WITH_CHROME=1`) exercises the new path.
- **The ILD container image is smaller (~2.06 GB → ~1.87 GB) with no change in functionality.** Four independent fixes: (1) with `WITH_DOTNET_SDK=1` the final stage is now based on `mcr.microsoft.com/dotnet/sdk:$DOTNET_VERSION` instead of layering a separately-downloaded SDK on top of `aspnet` — the old arrangement shipped two copies of the shared frameworks, since the SDK bundles its own. The base is selected by a `FROM final-base-${WITH_DOTNET_SDK}` alias, so `WITH_DOTNET_SDK=0` still yields the runtime-only image. (2) The published output is copied with `COPY --chown` rather than a trailing `chown -R /app`, which was rewriting every file into a second layer and shipping the app twice. (3) Chrome's `.deb` is installed with `--no-install-recommends` (plus an explicit `fonts-liberation`), dropping the mesa DRI driver set and the Noto font families that headless Chrome never loads — 941 MB → 746 MB on its own. (4) The `WITH_NODE` block no longer purges `ca-certificates`, which it did not install; that removal broke TLS for every later layer and was being silently repaired by a redundant reinstall further down, now also removed. `Dockerfile.WorkItemServer` gets the same `COPY --chown` fix.
- **CI now builds the container image on every PR** (`image-build`). Previously the Dockerfiles were only ever built by `publish.yml` at release time, so a Dockerfile regression failed the release tag rather than the change that introduced it. Only the shipped batteries-included amd64 image builds per PR — it `COPY`s each `.csproj` by name and runs the workspace `pnpm install`, so it also catches breakage from a new project or a dependency bump. The three targets that can only break when Docker-related inputs change — the `WITH_DOTNET_SDK=0` base that no other build selects, the WorkItem Server image, and arm64 under emulation — run in `image-extra.yml`, gated on a paths filter covering the Dockerfiles, `entrypoint.sh`, `.dockerignore`, `**/*.csproj`, `ILD.sln`, and the lockfiles, plus manual dispatch. Nothing pushes.

### Removed

- **BREAKING — the `DOTNET_SDK_CHANNEL` build arg is gone.** The SDK now comes from the `sdk:$DOTNET_VERSION` base image, so its version tracks `DOTNET_VERSION` and a separate channel knob no longer has anything to select. **Breaking for anyone who set it** — notably `DOTNET_SDK_CHANNEL=latest`, which installed an STS SDK independent of the runtime version; those builds now get the SDK matching `DOTNET_VERSION`. A stale `DOTNET_SDK_CHANNEL` in an existing `.env` is ignored rather than erroring. Dropped from `docker-compose.yml`, `.env.example`, and the configuration docs.

### Fixed

- **A finished run no longer keeps its concurrency slot for the lifetime of the process.** The scheduler's active work-item set was maintained incrementally, and the only release inside a poll pass fired when the server reported the item `Done` — so a run that ended with its item in Backlog, Ready or WorkQueue kept its slot forever. Five of those took effective concurrency to zero with no log line, an item could block itself (its own finished run holding the slot its next run needed), and a restart was the only recovery. The set is now derived once per pass from the runs ILD still considers alive, so a run that ends gives its slot back on the next pass whatever status its item landed in, and no termination path has to remember to say so. The same set is what the server's stale-item reclaimer is heartbeated with, so a leaked id no longer defeated that too. A pass that has Ready work but no room now names the items holding the slots, and stays quiet when the Ready queue is empty.
- **Sending a work item to Done ends its run.** Dragging a card to Done relabelled the item and left the run alone, so a run parked at a human gate stayed alive under a Done card — heartbeated, holding a slot, indefinitely; nothing else would end it, since the watchdog only reads `Running` runs and the retention sweeper only terminal ones. The Done transition now ends the run first, and the poll pass closes the same orphan when someone else finishes the item on a board shared between ILD instances ([ADR-0001](docs/adr/0001-standalone-workitem-server.md)).
- **Cancelling a run no longer leaves it Running.** Ending a run and choosing what its work item should say next are now separate steps — `ILoopEngine.StopRunAsync` ends a run and nothing else. That removes a stale-entity write that reverted a cancel back to `Running`, which left the run undriveable with its slot held and its worktree never reclaimed, and let the watchdog re-drive the very run a human had just cancelled. It also stops the Done, Backlog and delete paths flashing the item through **HumanFeedback** on the way out, with the permanent "Run cancelled" conversation entry and "needs attention" toast that came with it.
- **A run can no longer sit `Running` with a completion timestamp, or with two nodes marked Running at once.** Re-driving a finalized run (retry or resume) could flip it back to `Running` without clearing `CompletedAt`, and a crash left the in-flight node `Running` so the next drive started a second one. The contradiction is now unpersistable at the save boundary, each drive interrupts stale Running nodes once at the single point where a driver takes over, and `StuckRunWatchdog` heals runs already stuck that way — finalizing the run, collapsing its nodes to `Interrupted`, and parking the item for review. A failure while healing one run no longer aborts the whole sweep.
- **A work item overridden onto a different AI provider is no longer stranded or flapping.** The resume capacity check peeked at the AI node's pinned provider and ignored the work item's override, which the executor applies before claiming its slot — so an item overridden onto an idle provider waited behind a saturated provider it would never run against, and one overridden onto a saturated provider resumed, immediately re-parked, and emitted a status transition on every poll. The check and the executor's claim now resolve the provider through one shared rule, so they cannot drift apart again.
- **Pausing the scheduler now pauses only Ready→Running auto-promotion.** It used to short-circuit the entire poll cycle, freezing heartbeats, `WaitingForIld` resumes and Done cleanup along with it. Those keep running while paused, and a human can still promote a Ready item by hand.
- **A work item's file/diff view no longer collapses to "no files differ from the base branch".** The diff base was resolved solely through `origin/HEAD`, which is not set in ILD's worktrees, so a committed, clean worktree showed nothing at all. It now prefers the repository's stored default branch (`origin/<branch>`, then bare `<branch>`) and falls back to `origin/HEAD` only when that is unset or unresolvable — still pinned via `merge-base`, so a later fast-forward on the base branch does not pollute the diff.
- **The Files-tab diff keeps its tint across a horizontal scroll.** A changed line's background painted only as far as the panel's visible width, so the rest of a wide line rendered on the plain panel. Rows now size to their own content, and short changed lines end flush with long ones instead of leaving a ragged right edge.
- **Starting a work item no longer fails at the Start node with `Access to the path '/home/ild/.local/bin' is denied`.** The entrypoint's config-store linking chowned only the immediate parent of a nested link, leaving intermediate directories that `mkdir -p` created root-owned — so the orchestrator could traverse but not write them. The whole chain between `$HOME` and the link's parent is now chowned, to the orchestrator's _private_ group rather than the shared agent group: the agent uid gets no write access to a directory that sits on the orchestrator's `PATH`, which would have been exactly the cross-uid tool shadowing [ADR-0014](docs/adr/0014-agent-uid-isolation.md) exists to prevent.
- **ILD no longer seeds a stub `opencode.json` into every worktree**, where the run's `git add -A` swept it into the commit and the PR — for every repository, whatever adapter the loop actually used. It served no purpose: the OpenCode adapter passes `--dir` explicitly and supplies its config in memory.
- **The taskboard no longer freezes after a transient SignalR reconnect.** A reconnect gets a new connection id and so drops out of the server's work-items group, and nothing re-joined it — the board looked connected and received nothing until a reload. It now re-subscribes on reconnect and re-fetches the board (and the scheduler's paused state) to recover events delivered during the outage. A duplicate handler registration that fired every work-item event twice is gone as well.
- The terminal no longer reports a raw "Connection closed (1006)." on an ordinary idle or proxy timeout: a clean close is silent, a connection dropped after opening says so plainly, and one that never opened shows the caller's connect hint. The server's WebSocket keep-alive is also shortened to 30s, cutting idle-timeout drops at the source.
- A tall human-feedback prompt no longer pushes the Approve/Reject buttons off screen — the card is bounded by its panel and scrolls internally, and the prompt is capped to the space between its top and the bottom of the window.
- The **Preview** tab live-updates when an AI starts or stops a preview through the agent API, instead of staying stale until a manual reload.
- The chat bubble's provider list is no longer empty when you end a chat and return to the start form after a failed initial load.
- Clicking **Delete** on a repository no longer opens the "New Repository" form as an overlay across the Confirm button, which made the delete impossible to complete.
- A Pi custom provider now writes `$ILD_PI_PROVIDER_API_KEY` into the generated `models.json` instead of the bare variable name, which Pi treats as a literal credential — backends such as vLLM rejected it with 401 Unauthorized.
- An edge's **max traversals** cap survives a save and a reload. The loop editor persisted the reviewed export snapshot, which omits the field, so every save silently cleared any cap that had been set.
- PR-merge event-log entries (`PrMerged`, `PrMergeFailed`, `BranchDeleteFailed`) are recorded under their own types instead of being coerced to `Error`, so a successful merge no longer reads as a failure in the run timeline.
- **A work item keeps its pull requests forever, including after it moves to Done.** A work item had no PR field of its own: `WorkItemView.PrUrl` was projected from the item's _current_ run, and a finished run is not current — so the moment a run completed (engine Cleanup, or a human sending the item to Done) the PR link, branch and badges vanished from the taskboard and the detail dialog even though the `LoopRun` row still held the URL, and later the retention sweeper deleted that row and the link was gone for good. An item retried across several runs could never show more than one PR either, though ADR-0008 gives each run its own. Work items now carry **PR History**: a new add-only `pullRequests` collection on the work-item API (url, runId, merged, last known status, createdAt) listing every PR ever opened against the item, newest run first and deduplicated by URL. A PR touches the repository and is part of the work item — unlike the worktree, branch and PR snapshot, which are throwaway ILD-local run state — so it is stored **on the WorkItem server** (ADR-0001's source of truth, a new `PullRequestsJson` column and `POST /workitems/{id}/pull-requests`), not in the ILD database. It therefore also survives the ILD instance being reset or replaced. The PR node reports a PR as it creates it, the webhook path reports the merge, and any PR a live run still carries is re-reported on read, so a link lost to a crash or an unreachable server is one read away from being durable again. Per ADR-0002 `prUrl` is untouched and keeps its narrower "current run's PR" meaning for existing clients. The detail dialog's Overview panel renders the full list instead of a single link, and a board card shows how many PRs the item opened.
- **A PR can be linked to a work item that has no active run.** `POST /api/v1/workitems/{id}/link-pr` wrote the URL onto the item's current run and returned false when there was none, so a finished item — exactly the case where a human is filling in the PR after the fact — could not be linked at all. The link is now recorded against the work item itself, and the current run (when there is one) still gets the URL for the PR heartbeat.
- **Copilot runs no longer crash on persistence with an opaque EF Core error.** The `copilot` provider forwards the CLI's raw terminal stdout verbatim (unlike the JSON-parsing claude-code/opencode/pi adapters), and a raw stream can carry a NUL (U+0000) byte. A NUL cannot be stored in a PostgreSQL `text`/`varchar` column, so persisting the node output threw a `DbUpdateException`, crashing the run into `HumanFeedback` with only the generic "An error occurred while saving the entity changes. See the inner exception for details." `CopilotAdapter` now scrubs NUL from captured stdout/stderr (keeping every visible character), and — as a defense-in-depth backstop for any future raw-forwarding code path — `AppDbContext.SaveChanges` scrubs NUL from every string column being written, so the result persists. Zero-token/zero-cost accounting for the subscription-auth Copilot CLI is recorded as before (provider name stamped, token/cost columns null).
- **Crash reasons now surface the inner exception.** When a run crashes on an unhandled exception (e.g. a failed `SaveChanges`), the engine now flattens the whole inner-exception chain into the run's `HumanFeedbackReason` and the work-item conversation instead of only the outermost message — turning "See the inner exception for details." into the actual constraint/column cause, provider-agnostically. The flattened reason is clamped to the column's 512-char limit (with an ellipsis) so the crash handler's own save can never overflow and leave the run stuck `Running`.
- The WorkItem server's stale-reclaim and work-queue reconcile background services are now registered only when a database connection string is configured. Previously they were registered unconditionally but resolve a `WorkItemServerDbContext` that is registered only when `WORKITEM_DB_CONNECTION_STRING` is set, so a DB-less process crashed both services on every pass ("Unable to resolve service for type 'WorkItemServerDbContext'"). With a connection string set (the standard deployment) they run exactly as before.

### Security

- **The coding agent now runs under its own OS user, separate from the orchestrator** — see [ADR-0014](docs/adr/0014-agent-uid-isolation.md). The agent executes untrusted model output with permissions bypassed, and sharing a uid with the orchestrator meant it could `ptrace` its way to the orchestrator's memory, database handles and repository tokens, and read its private files. Every adapter (Claude Code, OpenCode, Copilot, Pi, and OpenCode's session export/import) now launches through one `AgentUserLauncher` seam that wraps the command in `setpriv --reuid=agent … --inh-caps=-all --ambient-caps=-all`, so the OS is a real boundary; ILD's own process work — git, npm — deliberately stays with the orchestrator. The published image ships the split on: an `agent` uid and a shared `ild-agents` group, shared directories carrying group ownership, setgid and default ACLs so both uids can work in them, `/data` orchestrator-private but traversable, and the credential store symlinked into both homes so one CLI login still serves both. Set `AGENT_USER=` in your `.env` to fall back to the single-uid behavior; local development, the test suite, and any deployment that does not set it are unchanged.
- **Orchestrator secrets are stripped from the agent's environment.** .NET pre-populates a child process's environment from its parent, so the split gave the agent its own uid but still handed it the database connection strings, `ILD_SECRET_KEY`, `ILD_PASSWORD`, and the API tokens the orchestrator uses to reach itself and the WorkItem server — an accepted residual in ADR-0014, now closed. The spawn path removes those names outright and the PTY login path neutralizes them to empty. The list is by exact name rather than pattern, because the adapters set the agent's _own_ credentials on the same environment under different names; a deployment can extend it with `ILD_AGENT_ENV_DENYLIST`. The git commit identity and the per-run MCP callback token are deliberately kept.
- **An untracked `.env` or `.ild.env` can no longer be swept into a run's commit.** A run commits with `git add -A`, so a secret dotenv a repository forgot to `.gitignore` could reach the PR. Both paths are now written into the worktree's git-local `info/exclude` before the add — never pushed, and only affecting untracked paths, so a repository that deliberately tracks its own `.env` still commits its edits.
- **The `ild` and `workitem-server` containers now run with `no-new-privileges`.** `security_opt: ["no-new-privileges:true"]` makes the kernel refuse any privilege gain on `execve` — setuid/setgid bits and file capabilities are ignored — for every process in those containers. It matters most in `ild`, where the lower-trust `agent` uid (see [ADR-0014](docs/adr/0014-agent-uid-isolation.md)) runs alongside the orchestrator; it removes setuid binaries as an escalation route from that uid. Nothing in either image relied on such a gain, so behavior is unchanged: the orchestrator drops privilege with `capsh` while retaining ambient capabilities and spawns the agent through `setpriv` rather than a setuid helper (chosen in ADR-0014 precisely to be compatible with this flag), the WorkItem server drops with `gosu`, and headless Chrome already runs with `--no-sandbox` on every launch path so it never needs the setuid `chrome-sandbox` helper. A missing `security_opt:` line has no runtime symptom, so a new CI test (`.github/scripts/compose-security-opt.test.sh`) asserts the flag per service rather than letting it regress silently in a future compose refactor. `postgres` is left untouched, to avoid coupling to a third-party image's entrypoint across version bumps.
- Pin `Microsoft.OpenApi` to 2.7.5 in the API and WorkItem server, off the vulnerable 2.0.0 pulled transitively by `Microsoft.AspNetCore.OpenApi` (GHSA-v5pm-xwqc-g5wc).

## [0.4.0] - 2026-06-25

### Added

- **AI Providers page** — a redesigned page that lists each managed coding agent (Pi, OpenCode, Claude Code) with its installed and latest version and a single action button: **Install** when nothing is installed, **Update {old} → {new}** when behind, **Up to date** when current, and **Unavailable** when not installed and the npm registry can't be reached.
- **Managed coding agents** — Pi, OpenCode, and Claude Code are installed onto the persistent `/data` volume on demand (npm install into a versioned dir followed by an atomic `current` pointer-file swap) and resolved from there at launch; an explicit config `binaryPath` still wins, and the baked-in/PATH copy remains the offline fallback. New `GET /api/v1/managedagents` and `POST /api/v1/managedagents/{key}/update` endpoints back the page.
- **Automatic agent provisioning** — a `ManagedAgentProvisioner` hosted service installs every agent an existing provider uses at startup, and on demand when a provider for a not-yet-installed agent is added or changed, so a fresh or freshly upgraded deployment no longer fails its first AI run on a missing CLI. Installs run detached and best-effort, never blocking host startup or the HTTP request.
- Chat now shows an in-progress indicator for the whole turn — "Thinking" before any tokens, "Responding" while text streams — with an animated pulsing dot that respects `prefers-reduced-motion`, so an in-flight reply is no longer indistinguishable from a finished one.

### Changed

- **Coding agents are no longer baked into the container image** — the `WITH_OPENCODE` / `WITH_PI` / `WITH_CLAUDE_CODE` build args and their Dockerfile install blocks are removed, and dropped from `docker-compose.yml`, `.env.example`, the publish workflow, and the configuration docs. A fresh deployment installs each agent once from the AI Provider page, and installs persist on `/data` across redeploys. `WITH_NODE` stays — Node/npm is what the runtime installs and version checks use.
- An agent update keeps the previous install alongside the new one (pruning bounded to two installs, current + previous) so an in-flight run that lazily `require()`s files from its version dir isn't pulled out from under it mid-update.
- **Event-log payloads are stored inline in Postgres** instead of being offloaded to a file when over 10 KB. Postgres already TOASTs and compresses large text values out-of-line, so the offload bought nothing while creating split state, a second read path, and a data-loss bug (every redeploy wiped the payload files but kept the rows, so the payload fetch 404'd forever). A startup `EventLogPayloadInliningMigrator` slurps any previously offloaded files back into the row and clears dangling paths, and the now-dead `/events/payload` endpoint, `hasPayload` flag, and payload-file retention/delete paths are removed.
- **Image publishing is release-only** — CI now pushes the GHCR images (`ghcr.io/tonyhopland/ild` and `ghcr.io/tonyhopland/ild-workitem-server`) only on a `vX.Y.Z` release tag, not on every merge to `main`. The moving `main` image tag is dropped. See [ADR-0012](docs/adr/0012-ghcr-image-tagging-strategy.md).

### Fixed

- Stranded WorkQueue items are now reconciled by a new `WorkQueueReconciler` background service: an item that enters the queue with its dependencies already Done, or one left behind by a crash or a lost promotion under concurrent completion, is promoted to Ready instead of waiting forever for a Done transition that will never fire. Deleting a work item also scrubs its id from every other item's dependency list, so dependents are no longer blocked permanently by a dangling dependency.
- A parked human-feedback node resumed via `SignalNodeResultAsync` — from the automated PR/CI poller, webhook PR sync, or an actual human response — now moves the work item out of the HumanFeedback column to Running, mirroring the other resume paths, so the board and the engine no longer diverge while the run executes.
- A human-feedback node no longer renders a stale `{{Var.*}}` value: `GetVariablesAsync` now reads with `AsNoTracking()` so it returns fresh column values after `set_loop_variable` updates a variable from a separate scope, instead of an already-tracked stale instance via EF identity resolution.
- The AI Provider "Open terminal" action now resolves the CLI from the agent's `/data` install (or PATH) the same way the loop adapters do, instead of a bare command name that isn't present on a fresh machine, and sends an actionable "install it from the AI Provider page" message when nothing resolves rather than an opaque PTY spawn error.

## [0.2.0] - 2026-06-15

### Fixed

- A run's worktree and per-run branch now live exactly as long as its run row: only run deletion — manual (`DELETE /api/v1/loopruns/{id}`, work-item delete) or the retention sweeper — destroys them, through a shared `IRunReclaimer` with a fallback that locates the base repo through the run's Repository when the worktree is already gone. Sending a work item to Done/Backlog finishes the run but keeps its worktree and branch inspectable. The run row is only deleted once reclamation is verified (manual delete returns 409 on failure), so a failed worktree/branch delete is retried by a later sweep instead of leaking untracked disk. Spilled event-log payload files are deleted together with the run.
- The engine now reloads the run row before persisting each node outcome, so pausing, cancelling, or pinning (`Retain`) a run during a long node execution is no longer silently reverted by the node's completion write — previously a pinned run could still be deleted by retention and a cancel could be undone.
- Startup reconciliation now includes runs parked at Human/PR nodes (`WaitingHuman`) and re-tracks their work items so server heartbeats resume — previously the stale-item reclaimer would hand the item to a second concurrent run ~15 minutes after a human resumed it. Runs whose work item the server has since finished, reclaimed, or deleted are cancelled instead of being blindly resumed into a duplicate, and recovery honors the template's `RecoveryPolicy` (which is now actually pinned onto each run at start).
- A work item claim whose run fails to start (e.g. broken template) is handed back to HumanFeedback instead of remaining stuck in Running while heartbeated forever, permanently occupying a scheduler slot.
- A PR-merge webhook now books the merge on the run that owns the PR (matched by URL). Merging an old run's still-open PR no longer marks the current run merged or flips the work item to Done while another run is mid-flight, and a merge no longer marks the work item Done before the resumed run has executed its post-merge nodes.
- The worktree retention sweeper re-checks each run's status and `Retain` pin just before reclaiming (a run retried back to Running mid-sweep is left alone), and its first pass now happens 10 minutes after startup instead of 6 hours, so frequently-restarted deployments still reclaim disk.
- A run can no longer get permanently stuck in Running with no task driving it. The engine's launch path is now single-owner — one atomic ownership claim per run, so a launch/relaunch race (e.g. the periodic scheduler's resume colliding with a live loop) can't start a second loop or leave a run un-driven — and `ResumeRecoveredRunAsync` no-ops on an already-driven run instead of clobbering its in-flight node. A new `StuckRunWatchdog` background service is the backstop: every minute it recovers runs that are Running with no live driver (honoring the run's `RecoveryPolicy`), covering crash modes the engine's own exception handler can't see. It keys on absence of a driver, never elapsed time, so a legitimately long-running AI node is never interrupted; runs intentionally parked by the capacity gate (work item `WaitingForIld`) or awaiting a human are left for the scheduler/human to resume.
- The Start node now fails fast when the base-repo fetch fails instead of starting from stale state.
- Work item `Started`/`Completed` timestamps are populated from the latest run.
- The file explorer and Changes view live-refresh; folders collapse by default in the explorer and expand by default in the Changes view.
- Numeric work item status from SignalR events is normalized to the correct `RemoteWorkItemStatus` ordering, fixing mismatched board placement.
- The live view no longer clips the last line of output, and the new work item dialog clears its fields when reopened.

### Security

- Provider API keys and webhook secrets (`RemoteProvider.ApiKey`/`WebhookSecret`, `AiProvider.ApiKey`) are now encrypted at rest with AES-256-GCM when the new `ILD_SECRET_KEY` environment variable is set. Behaviour is backwards-compatible: when the key is unset, secrets are stored as plaintext and a startup warning is logged; legacy plaintext rows remain readable after a key is added. See [docs/configuration.md](docs/configuration.md#secret-encryption-at-rest).
- Webhook secrets are now masked (`***`) in `GET /api/v1/remote-providers` responses, matching the existing treatment of API keys, and a `hasWebhookSecret` flag indicates whether one is set.
- Added [SECURITY.md](SECURITY.md) documenting the trust model and vulnerability reporting process.

### Changed

- AI nodes now use a single `prompt` field regardless of whether they run in a fresh or resumed session; prompt variation across turns is now modeled explicitly with `Prompt` nodes in the graph.
- AI adapters now always receive one prompt from the AI node; session handling only controls binding and resume behavior.
- Opencode managed session import/export now only runs for AI nodes that explicitly enable session usage.
- The seeded templates now insert `Prompt` nodes ahead of session-backed AI nodes wherever the first turn should differ from later follow-up turns.
- Each run now gets its own git branch (`ild/wi-<workItemId>-run-<runId>`) and worktree instead of a shared per-work-item branch — this fixes prior-run commits leaking into a new run via rebase. The Cleanup node no longer destroys the worktree; finished runs keep their worktree so they stay inspectable, and re-running a work item now opens a separate PR per run.
- Loop tags are visually distinguished (purple background) from other tags in the taskboard filter chips.
- The engine enforces at most one active run per work item, closing a race that could start two concurrent runs.

### Added

- A `WorktreeRetentionSweeper` reclaims a finished run's worktree, branch, and record once it has been terminal longer than the configurable `run.retentionDays` setting (default 30; `0` disables; the run a still-active work item points at is preserved). Individual runs can be pinned with **Retain** (`PUT /api/v1/loopruns/{id}/retain`) so retention never deletes them. See [ADR-0008](docs/adr/0008-worktree-and-branch-per-run.md).
- Added a `Prompt` loop node type that renders a prompt template with the same placeholder-aware editor used by AI and PR prompt fields, then emits the rendered text as node output.
- Added a **Push branch** button to the work item overview (`POST /api/v1/workitems/{id}/push-branch`) that commits all uncommitted changes in the current run's worktree and pushes its branch to origin, using the same built-in repository functionality as the PR node — for keeping work produced by a loop that has no PR node.
- The work item overview now shows a **Loop** row while an item is mid run, naming the run's pinned loop template and the node the engine is currently on (e.g. `build-loop · Implement`).
- The work item dialog is now a full-screen, tabbed view (Overview, Conversation, Runs, Files, Terminal) replacing the previous in-dialog switcher. Edit moved to the footer and Delete now lives inside the edit view.
- **Run analytics & AI cost dashboard** — durable usage rollup with per-provider and time-range filters surfacing run counts, throughput, and token/cost trends.

- A **Files** tab with a live file explorer and a **Changes** diff view in the work item dialog.
- **Retry from node** on the work item Runs tab, re-entering a run at a chosen node.
- A **Merge** action (with optional delete-branch) on the PR-feedback panel.
- Named **custom edges** generalize node edge routing; AI nodes now route solely via match rules, with editor support for connected custom edges on AI/Human/PR nodes.
- Taskboard search plus repository and tag filters; running cards show the current step and elapsed time, and the Backlog and Done columns paginate. Loop creation and work-item creation now broadcast so the board updates live.
- Work items are deep-linkable via URL, always opening the detail dialog on the Overview tab.
- Opt-in `ild.config` tool install on the Start node, exposed to agents during preview.
- Example loop templates are seeded on a fresh install.
