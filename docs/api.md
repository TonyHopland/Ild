# API Design

ILD exposes **two distinct HTTP surfaces**. Keeping them separate is deliberate — see [ADR-0001](./adr/0001-standalone-workitem-server.md).

| Surface                 | Host                 | Audience                                               | Auth                                                          |
| ----------------------- | -------------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| **ILD application API** | `ILD.Api`            | The SPA, operators, and the agent-facing MCP tooling   | Bearer-token session (cookie/header)                          |
| **WorkItem Server API** | `ILD.WorkItemServer` | ILD instances coordinating over shared work-item state | API key (`Authorization: Bearer <key>` or `X-Api-Key: <key>`) |

The ILD application API is mounted under `/api/v1/...`; the standalone WorkItem Server mounts its routes at the root (`/workitems`, `/health`). Realtime updates flow over SignalR, not REST.

## Conventions

- **Versioning.** Routes carry a hand-written `/api/v1` prefix rather than the `Asp.Versioning` package. Breaking changes introduce a new prefix and keep the old one alive until clients migrate — see [ADR-0002](./adr/0002-manual-api-versioning.md).
- **Auth scope.** Bearer auth is an authentication scheme with a deny-by-default authorization policy: every endpoint requires an authenticated caller in the `user` role unless it opts out. Login, health, logging, metrics and the SPA fallback are anonymous; the agent surface (`/api/v1/agent/...`) and the webhook routes accept any authenticated caller, so an agent token reaching anything else is refused with 403. Webhook routes additionally require HMAC verification on top of bearer auth. Static assets are served before authorization runs, so the shell can load. The `/metrics` endpoint is served at the root.
- **Pagination.** List endpoints accept `skip`/`take` (default 100, capped at 500). Event-log queries are cursor-paginated and cap `limit` at 500 server-side.
- **Taskboard listing.** `GET /api/v1/workitems/page?status=&repositoryId=&search=&tags=&skip=&take=` answers `{ items, total }` for one board column in board order, where `search` matches the title, description or id and an item must carry every `tags` value. `status` may repeat (`status=WorkQueue&status=Ready`, as the Work queue column reads): the page then spans every given status in one board order and `total` counts the items in any of them; without a `status` it spans every status. A Done transition through this ILD instance also announces, as a `WorkItemStateChanged` from WorkQueue to Ready, each dependent the WorkItem Server promoted with it; promotions by the server's `WorkQueueReconciler`, by deleting the item a dependent waited on, or by another instance are not announced and show on a board's next read. `GET /api/v1/workitems/counts` takes the same filter and answers the total for every status; `GET /api/v1/workitems/tags` lists every tag in use, once whatever its case. An unknown `status` among those given or a `repositoryId` that is not a GUID is refused with 400.
- **Board order.** A work item's `priority` is a number giving its place on the board: the lowest comes first, and equal values go by id, shorter first and then ordinal. A new item gets a value below every other item's, so it starts at the top of its column, and a status change never alters it. `POST /api/v1/workitems/{id}/reorder` `{ aboveId?, belowId?, targetStatus? }` moves a card to where it was dropped, naming the cards directly above and below that spot in its column: with `aboveId` the item lands directly after that card in the whole board's order, otherwise directly before `belowId`. A `targetStatus` other than the item's own moves it into that column in the same request, under the same rules as `POST /api/v1/workitems/{id}/transition`; the item either lands in place in its new column or stays where it was. It answers 200 with the item, 400 when neither neighbour is given, one is the item itself or no item, the status does not parse or the move is not allowed, and 404 for an unknown item. The moved item is announced as a `WorkItemStateChanged`, with its status unchanged for a drop within a column and as its transition announces it otherwise. When no number is left between the neighbours the whole board is renumbered in the same order, announced once as `WorkItemBoardReordered` `{ workItemId }`, on which a board re-reads its columns. User-only. The WorkItem Server does the placement, the renumber and the move in one transaction: `POST /workitems/{id}/reorder` `{ aboveId?, belowId?, targetStatus?, actions?, reason? }` answers 200 `{ outcome, item, renumbered, reason }` for every outcome, `outcome` being 0 (moved), 1 (no such item), 2 (an invalid neighbour) or 3 (the transition was refused, `reason` saying why). The scheduler starts the top-most Ready item that may start. Agents read the value as `priority` on `GET /api/v1/agent/workitems`, which `orderBy=priority` sorts in board order, and on `GET /api/v1/agent/workitems/{id}`. The old `priority` filter on `GET /api/v1/agent/workitems` is refused with 400, pointing at `orderBy=priority`.
- **Errors from AI providers** surface as `AiProviderException` with cause-preserving inner exceptions.
- **Advisory checks are not gates.** `GET /api/v1/workitems/branch-name-check?name=&repositoryId=&workItemId=` answers `{ error, warning }` for a work item's custom branch name while it is being typed. `error` (an illegal git ref) is also enforced on create and edit and will fail the save; `warning` (the name is already taken) never blocks one, because the authoritative check is the one the engine takes at run start — see [ADR-0008](./adr/0008-worktree-and-branch-per-run.md).
- **Sessions are plural.** `POST /api/v1/auth/login` mints one session per device and reports its `expiresAt` (null when the absolute cap is disabled); `POST /api/v1/auth/logout` revokes only the calling one. `GET /api/v1/auth/sessions` lists the caller's own live sessions — an opaque `id`, `createdAt`, `lastSeenAt`, `expiresAt`, `userAgent`, `createdFromIp`, and `isCurrent`, never a token or a token hash. `DELETE /api/v1/auth/sessions/{id}` revokes one (404 when it is not a live session of the caller); `POST /api/v1/auth/sessions/revoke-others` revokes every session but the calling one and answers `{ revoked }`.
- **Work item branch fields.** `branchNameOverride` (the branch a run uses) and `baseBranchOverride` (the branch it starts from and opens its PR against) are accepted on create and update, on both `/api/v1/workitems` and the agent surface, and returned on read. Both follow the same convention: omitted means "not part of this edit", an empty string clears the override back to the default. Both are validated as git ref names on save; whether a base branch actually _exists_ is not, because that is only answerable — and only binding — when the run starts.
- **Work item branch link.** `GET /api/v1/workitems/{id}` carries a read-only `branchUrl`: the forge web page of the current run's `branchName`, or null. It is non-null only when the run's worktree has the branch's remote-tracking ref (a local check, no fetch), the repository's provider is GitHub, Forgejo or Azure DevOps and its clone URL is http(s); the link never carries the clone URL's credentials. List reads never set it.
- **Work item attachments.** `POST /api/v1/workitems/{id}/attachments` takes `multipart/form-data` under the field `files` (at most 10 per request) and answers 201 with the created metadata; `GET /api/v1/workitems/{id}/attachments` lists `{id, fileName, contentType, sizeBytes, createdAt}` and never the bytes; `GET`/`DELETE /api/v1/workitems/{id}/attachments/{attachmentId}` serve one file (always as `Content-Disposition: attachment`) and remove it. `GET /api/v1/settings/attachments` reports the limits a client should enforce before uploading — `{ maxBytesPerFile, maxFilesPerRequest, maxTotalBytesPerWorkItem }` — and a file breaking any of them is a 400 naming it, from the ILD API or from the WorkItem server behind it, which enforces the same limits independently. Agents read but never write: `GET /api/v1/agent/workitems/{id}` carries the same metadata and `GET /api/v1/agent/workitems/{id}/attachments/{attachmentId}` the bytes, and there is no agent route that uploads or deletes one. The WorkItem Server carries the same four routes under `/workitems/{id}/attachments`, where the bytes live.
- **Agent work item dependencies.** `POST /api/v1/agent/workitems/{id}/dependencies` with `{ dependsOnWorkItemId }` makes the item wait on another, and `DELETE /api/v1/agent/workitems/{id}/dependencies/{dependsOnId}` removes that edge. Only the dependent item `{id}` must have been created by the caller's session (the `update_workitem` rule); anything else is a 403 pointing at `propose_workitem_edit`. An unknown `{id}` is a 404; a blank, unknown or self `dependsOn`, or an edge that would create a cycle, is a 400. Both answer 200 `{ workItemId, dependsOnWorkItemId, changed, message, dependencies: [{ id, title, status }] }` listing the dependencies after the call; adding an existing edge or removing an absent one is `changed: false` and changes nothing. They go through the same path as the human `/api/v1/workitems/{id}/dependencies` routes, so status follows the same way.
- **Agent loop retro reads.** Four read-only GETs on the agent surface let an agent review how loops performed. `GET /api/v1/agent/analytics/templates?from=&to=&provider=&templateId=` answers `{ from, to, provider, templateId, templates }`, each template row carrying the analytics dashboard's figures for the same filters (deleted runs included, same order) plus per-node `executions`, `failures` and `avgSeconds` keyed by node id from the `runsWithNodeDetail` runs that still exist. `GET /api/v1/agent/loop-runs` takes `from`, `to` and `templateId` beside `workItemId`, orders newest first by start (creation for an unstarted run) then id, and adds `templateId`, `templateName` and `templateVersion` to each row. In both, `from`/`to` are inclusive `yyyy-MM-dd` UTC days on the run's start, and a malformed date or a non-GUID `templateId` is a 400 naming it. `GET /api/v1/agent/loop-templates/document?nameOrId=&version=` answers `{ templateId, version, latestVersion, isLatest, versionCreatedAt, isArchived, document }`, where `document` is an `ild-loop-template/v2` document that `PUT /api/v1/agent/current-loop` accepts unchanged, written as one fixed rendering (compact, camelCase, the default encoder's `\uXXXX` escapes) that an Edit List's `editFile` matches against; its name, description and recovery policy are the template's current values. `nameOrId` is a template id or an exact name (case and surrounding whitespace ignored, archived templates included; a GUID that is no template's id is tried as a name): no match or an absent version is a 404 (the latter naming the latest), a name several templates share is a 409 listing `candidates`, and `version` below 1 is a 400. `GET /api/v1/agent/loop-runs/{id}` summarises one run: its header and counters, every node visit in execution order with its outcome, duration, `incomingEdge` and `edgeTaken` (the edge a later visit that came from this one entered by, when it leaves this node; for the last visit, if it also completed last, the edge the run has followed from it toward its current node; otherwise null), its human-feedback requests and answers and its parks (`parked` also covers ILD's own waits, such as an AI provider throttle, with the reason in `text`), and its pull request with the review comments from the last stored PR snapshot (nothing is fetched from the forge). Its free texts (node errors, the feedback reason, feedback texts and comment bodies) are cut at 2000 characters and flagged; node output, inputs and transcripts are never included. A non-GUID id is a 400, an unknown run a 404.
- **Work item edit proposals.** An agent may propose an edit to any work item with `POST /api/v1/agent/workitems/{id}/edit-proposals` — any of `title`, `description`, `tags`, `branchNameOverride`, `baseBranchOverride` (omitted means "not proposed", an empty override proposes clearing it), `addDependencies` and `removeDependencies` (lists of work item ids) plus an optional `rationale` — and gets 201 `{ id, workItemId, status: "Pending" }`. The caller's session header must name an existing loop run or chat session (400 without one, 403 for an unknown one); a proposal that fails the same checks as an update, or proposes nothing, is a 400, and a 21st pending proposal on one item is a 409. A dependency list naming a blank, repeated or unknown id, the item itself, an id in both lists, an addition that is already a dependency or would create a cycle, or a removal that is not a dependency, is a 400. Proposals read back with `proposed.addDependencies` / `proposed.removeDependencies` as `[{ id, title }]` (title null once that item is gone) and `snapshot.dependencies`, the item's dependency set when a dependency change was proposed. `GET /api/v1/agent/workitems/{id}/edit-proposals` lists an item's proposals with their status and rejection reason. Nothing applies until a human decides on the user-only surface: `GET /api/v1/workitems/{id}/edit-proposals`, `GET /api/v1/workitems/edit-proposals?status=&chatSessionId=`, `POST /api/v1/workitems/{id}/edit-proposals/{proposalId}/approve` (200 `{ proposal, workItem }`; 409 `{ error, proposal }` when the item changed since the proposal was made, which leaves the proposal `Stale`, or when it was already decided; 422 `{ error, proposal }` when an added dependency would now create a cycle or no longer exists, which leaves it `Pending`) and `POST .../reject` with an optional `{ reason }` of up to 2000 characters (200 with the proposal). The list and decision responses carry `createdByRunNodeId` (the loop run step that was running when the proposal was made) and `chatReplySequence` (the sequence of the chat reply it follows), which ILD records from its own state, never from the request body; they place each card in the requesting item's Action tab or in its chat, and are null when there was nothing to anchor to. Every proposal ILD returns also carries `requestedByWorkItemId`: the work item whose loop run made it, read from that run, and null for a chat's proposal or once the run no longer exists. `GET /api/v1/workitems/{id}/requested-edit-proposals` lists what the item's own loop runs proposed, on any item, newest first; these are the cards its Action tab decides. Deleting a loop run, by `DELETE /api/v1/loopruns/{id}`, by deleting its work item or by the retention sweep, first rejects its still-pending proposals with a reason saying the run was deleted; if the WorkItem Server cannot be reached the run is kept (the user delete answers 503) so a later delete or sweep retries. The WorkItem Server holds the proposals under `/workitems/{id}/edit-proposals` and `/edit-proposals`, and makes an approve one atomic compare-and-apply ([ADR-0022](./adr/0022-agent-edits-are-human-approved-proposals.md)).
- **Work item history.** `GET /api/v1/workitems/{id}/history` answers the item's changes newest first, in the order they were written, one entry per field changed, `{ saveId, timestamp, kind, username, actorKind, actorDetail, actorWorkItemId, field, oldValue, newValue, reason }`: the entries of one save share `saveId`; `kind` is `Created`, `Baseline` (the values an item had when history began, seeded for items older than history), `Changed` or `Deleted`; `actorKind` is `Human`, `Agent`, `Chat` or `System`; `actorWorkItemId` is the work item the acting loop run was working on, which ILD fills in for a baseline of an item one of its own runs created; `oldValue` is the previous entry's value for the field and null for its first entry. The tracked fields are `title`, `description`, `status`, `tags`, `dependencies` (JSON arrays as stored), `repository`, `aiProviderOverride`, `aiProviderOverrideId`, `branchNameOverride` and `baseBranchOverride`; enums are written by name and an unset field is null. The `priority`, now the item's place on the board, is not tracked, so a reorder writes no history; `priority` entries from before (`Low` to `Critical`) stay in an item's history. Events are fields of their own, never paired with an old value: `pullRequest.linked` and `pullRequest.merged` carry the PR's URL, and `deleted` (kind `Deleted`) the item's title when it was deleted. `reason` says why: on a `status` entry the transition's reason, on the fields an approved edit proposal changed its rationale. A deleted item's history stays readable; only an id with neither history nor an item is a 404, and an unreachable WorkItem Server is a 503. Agents get the same list as `history` on `GET /api/v1/agent/workitems/{id}?includeHistory=true` (the `get_workitem` tool's `includeHistory`), which is left out by default; for a deleted item that route is a 404 `{ error, history }`.
- **Agent network limits.** `GET /api/v1/network/status` answers `{ enforcement, reason, proxyEnabled, proxyPort, offAvailable }`, where `enforcement` is `enforced` or `advisory` — advisory means the proxy logs and filters proxy-honouring clients but the firewall behind it is not in place, and `reason` says why — and `offAvailable` is false when agents launched in `off` would have no network. `GET`/`POST /api/v1/network/entries` and `DELETE /api/v1/network/entries/{id}` manage the whitelist and blacklist; an entry is `{ host, listKind: Whitelist|Blacklist, aiProviderId? }`, the host is canonicalised on the way in (`*.example.com` becomes `.example.com`) and a URL, a port or an unknown provider is a 400 with the reason. `PUT /api/v1/network/entries/{id}` takes the same body and validation, answers 404 for an unknown id and 400 when the edit would duplicate another entry. `GET /api/v1/network/log?take=` (newest first, capped at 1000) and `DELETE /api/v1/network/log` read and clear the destination log; `POST /api/v1/network/log/{id}/whitelist` and `.../blacklist` promote a log line to a list, globally or — with `{ scopeToProvider: true }` — scoped to the line's provider, and answer 200 rather than a duplicate when the entry already exists. The mode toggle is the `network.mode` setting (`off|monitor|whitelist|blacklist`, default `monitor`) on the settings endpoint; anything else is a 400 naming all four. `monitor` allows and logs everything (what `off` meant before the rename; a stored `off` is migrated to `monitor` once at upgrade); `off` launches agents with no proxy at all, so they connect directly to any host and port, only connections through a forward are logged, and the DNS block does not apply (under an enforced firewall it needs `no-new-privileges`; setting `off` while `offAvailable` is false is a 400 with the status `reason`). A list edit or a change between proxied modes takes effect on the agent's next connection; switching to or from `off` takes effect on the next agent launch, and running agents keep what they started with.
- **Package feeds.** `GET`/`POST /api/v1/package-feeds`, `PUT`/`DELETE /api/v1/package-feeds/{id}` manage the private Azure Artifacts feeds; a feed is `{ id, name, feedUrl, patHint, createdAt, updatedAt, credentialProviderMissing }`. `POST` takes `{ name, feedUrl, pat }`; `PUT` takes `{ feedUrl, pat? }`, where an empty or absent `pat` keeps the stored one and the name cannot change. The PAT is never returned by any endpoint: `patHint` is `••••` plus its last four characters, or just `••••` for a PAT under eight. `credentialProviderMissing` is the same on every feed: true when a .NET SDK is installed but the Azure Artifacts credential provider NuGet would need for these feeds cannot be found. The feed URL must be `https://pkgs.dev.azure.com/{org}[/{project}]/_packaging/{feed}` or `https://{org}.pkgs.visualstudio.com[/{project}]/_packaging/{feed}` and is returned as entered, without a trailing slash; anything else, an empty or duplicate (ignoring case) name, or a missing PAT is a 400 with the reason. `POST /api/v1/package-feeds/{id}/test` makes one authenticated request for the feed's NuGet service index on the host its URL names and answers the same `{ ok, outcome, message, detail }` as the provider and repository tests. User-only: the agent token gets 403. Repositories take `packageFeeds` (feed names) on create and update — omitted on update keeps the selection, and a name that is neither a feed nor already selected is a 400 — and return it as `[{ name, missing }]`, `missing` once the feed has been deleted.
- **Global variables.** `GET`/`POST /api/v1/global-variables`, `PUT`/`DELETE /api/v1/global-variables/{id}` manage the instance-wide values prompts read with `{{Global.<name>}}`; a variable is `{ id, name, value, updatedAt, usedBy }`, listed by name, where `usedBy` is `[{ id, name }]` of the non-archived loop templates whose latest version uses it. `POST` takes `{ name, value }` and answers 201; `PUT` takes `{ value }` and the name cannot change. A name is trimmed and must be a letter followed by up to 127 letters, digits or underscores, unique ignoring case; an empty value is allowed, a missing one is not. A value longer than the `globalVariables.maxLength` setting (default 4000, 1–8192) is a 400 stating both lengths. User-only: the agent token gets 403. A run parked because its next node uses a missing or empty one has `haltReason: "GlobalVariableMissing"`, and both run endpoints carry `missingGlobalVariables`, the names still missing now (empty for every other run).
- **Loop template proposals.** Agents propose a change to a saved template with `POST /api/v1/agent/loop-templates/proposals` `{ nameOrId, baseVersion, document, edits, rationale }`, answered 201 `{ id, templateId, baseVersion, status: "Pending" }`. `nameOrId` resolves as `GET /api/v1/agent/loop-templates/document` does (404 unknown, 409 `{ error, candidates }` for a shared name). Exactly one of `document` and `edits` is sent; both, neither or an empty `edits` is a 400. `document` is the whole `ild-loop-template/v2` document as JSON text (a v1 one is upgraded), at most 1,000,000 characters. `edits` is an Edit List: an ordered array of Loop Editor edits, each `{ op: "editNodeField", nodeId, field, oldString, newString }`, `{ op: "setNodeField", nodeId, field, value }` or `{ op: "editFile", oldString, newString }`, applied in order to the latest version's document as `GET /api/v1/agent/loop-templates/document` renders it, with the same matching and messages as the open-loop edit tools; at most 1,000,000 characters as stored. The first edit that does not land is a 400 `{ error, editIndex }`, `error` being that edit's message prefixed `edits[i] (op, node 'x', field 'y'): `, and nothing is stored or superseded. Only the final document has to be a valid loop; `baseVersion` must be the template's latest version, else 409 `{ error, latestVersion }`. A document a Loop Editor save would refuse is a 400: `{ error }` for the document, name, description or policy, `{ error, validationErrors }` listing every graph error. The session header rules and supersede-per-source are those of global variable suggestions. `GET /api/v1/agent/loop-templates/proposals` lists the caller's own, newest first: `{ id, templateId, templateName, baseVersion, rationale, editCount, status, editedBeforeSave, appliedVersion, rejectionReason, createdAt, decidedAt }`, `editCount` being the Edit List's length (null for a whole document) and `status` being `Pending`, `Applied`, `Rejected`, `Stale` or `Superseded`. A human decides on the user-only surface: `GET /api/v1/loop-template-proposals?status=&templateId=&workItemId=&chatSessionId=` (each with `templateName`, `templateExists`, `baseVersion`, `latestVersion`, the creating run, step, chat and reply, `source: { kind: run|chat|deleted, workItemId, chatSessionId, linkable }` and `changes`, the nodes added, removed or changed and the edges added or removed against the base version, and `edits`, the Edit List as the server parsed it with null members dropped, or null for a whole document), `GET /api/v1/loop-template-proposals/{id}` (also the `document`), `GET /api/v1/loop-template-proposals/pending-counts` (`{ "<templateId>": n }`), `POST /api/v1/loop-template-proposals/{id}/save` (no body; 200 `{ proposal, version }`; 409 `{ error, proposal }` when the template has a newer version, which leaves it `Stale`, or when it was already decided; 404 unknown) and `POST .../reject` with an optional `{ reason }` of up to 2000 characters. `PUT /api/v1/looptemplates/{id}` takes an optional `fromProposalId` and answers `{ id, version, proposalApplied }`: the named proposal is applied when it is pending, of that template and based on the version the save follows. Every new version, and deleting the template, makes its pending proposals `Stale` ([ADR-0028](./adr/0028-agents-propose-loop-template-changes.md)).
- **Global variable suggestions.** Agents read the variables with `GET /api/v1/agent/global-variables` (`[{ name, value, updatedAt }]`, by name ignoring case) and suggest a new value with `POST /api/v1/agent/global-variables/proposals` `{ name, value, rationale }`, answered 201 `{ id, name, status: "Pending" }`. The value is the whole new text and may be empty; a name no variable has suggests creating it. The caller's session header must name an existing loop run or chat session (400 without one, 403 for an unknown one); an invalid name, a missing value, a blank rationale or one over 2000 characters is a 400, and so is a value over the `globalVariables.maxLength` setting, whose error states `<length> / <limit> characters`. A new suggestion from the same run or chat for the same variable supersedes that source's pending one. `GET /api/v1/agent/global-variables/proposals` lists the caller's own, newest first, with `{ id, name, value, rationale, status, rejectionReason, createdAt, decidedAt }`; `status` is `Pending`, `Approved`, `Rejected`, `Stale` or `Superseded`. A human decides on the user-only surface: `GET /api/v1/global-variables/proposals?status=&workItemId=&chatSessionId=` (each also carrying `snapshotUpdatedAt`, `currentValue`, `variableExists`, `createdByLoopRunId`, `createdByRunNodeId`, `createdByChatSessionId`, `chatReplySequence` and `source: { kind: run|chat|deleted, workItemId, chatSessionId, linkable }`), `GET /api/v1/global-variables/proposals/pending-count` (`{ count }`), `POST /api/v1/global-variables/proposals/{id}/approve` (takes no body; 200 `{ proposal, variable }`; 409 `{ error, proposal }` when the variable changed since the suggestion was made, which leaves it `Stale`, or when it was already decided; 404 for an unknown id) and `POST .../reject` with an optional `{ reason }` of up to 2000 characters (200 with the suggestion). Creating, editing or deleting a variable makes its pending suggestions `Stale`. Deleting the run, its work item or the chat that made a suggestion leaves it as it was ([ADR-0027](./adr/0027-agents-suggest-global-variable-changes.md)).
- **Human input suggestions.** Agents suggest the answer for a work item parked at a Human node with `POST /api/v1/agent/workitems/{id}/human-input-proposals` `{ output, text, rationale }`, answered 201 `{ id, workItemId, output, status: "Pending" }`. `output` is one of the node's outgoing edge names as `humanFeedbackActions` lists them (OnSuccess, OnFailure or a custom edge's name); `text` is the input sent with it, up to 8192 characters, and may be empty. The session header rules and supersede-per-source are those of global variable suggestions (400 without a session, 403 for an unknown one). An unknown work item is 404; one whose active run is not parked for "Human Input Needed" at a Human node is 409 `{ error }`; an output the node does not offer is 400 with the offered ones in `error`; a missing output, a blank rationale or one over 2000 characters, or text over 8192 characters is 400. A human decides on the user-only surface: `GET /api/v1/human-input-proposals?workItemId=&status=` (newest first, each `{ id, workItemId, runId, runNodeId, output, text, rationale, status, rejectionReason, decidedBy, createdAt, decidedAt, createdByLoopRunId, createdByChatSessionId }`; a missing `workItemId` or unknown `status` is 400), `POST /api/v1/human-input-proposals/{id}/approve` (no body; 200 `{ proposal }` once the answer is delivered as the matching human-feedback endpoint would; 409 `{ error, proposal }` when the suggested visit is no longer open, which leaves it `Stale`, or when it was already decided; 404 for an unknown id) and `POST .../reject` with an optional `{ reason }` of up to 2000 characters (200 with the suggestion; nothing is delivered). Answering a visit by any means, or cancelling, retrying or deleting its run, makes the pending suggestions for it `Stale` ([ADR-0030](./adr/0030-agents-suggest-human-input.md)).
- **Repositories in scheduled chats.** `POST /api/v1/agent/chat/repositories/{repositoryId}/clone` `{ branch? }`, with the calling chat in `X-ILD-Chat-Session-Id`, clones the repository into the chat's scratch folder under `repos/<name>` (a name made safe for disk, suffixed with the repository id when that name is already taken by anything but this repository's clone; a renamed repository keeps its folder), or updates the clone made there before. The branch defaults to the repository's default branch, else `main`; an update is fast-forward only, a different branch switches to it, and local work in the way is never discarded. It answers 200 `{ outcome: Cloned|Updated, path, branch, commit, previousCommit, changed, message }`, `path` relative to the chat's working directory and `previousCommit` null for a fresh clone. Without the header it is a 400 `{ error }`; every other refusal carries `{ error, outcome }`: 400 for an invalid branch name (`InvalidBranch`); 403 for an unknown chat (`UnknownChat`), a chat no schedule started (`NotScheduledChat`) or a repository the schedule's allowlist, read at each call, leaves out (`NotAllowed`); 404 for an unknown repository (`UnknownRepository`) or a branch the remote lacks (`BranchNotFound`); 409 when git would lose local work (`UpdateRefused`, with git's message; nothing changed); 502 when ILD cannot clone or fetch its own copy of the repository (`FetchFailed`); 500 when a step in the chat's clone itself fails (`CloneFailed`, with git's message). ILD fetches its own base clone with the remote provider's credentials and fills the chat's clone from it as the agent user, so the clone's `origin` and files hold no credentials. The work finishes even if the request is cancelled, so a caller that timed out calls again.
- **Storage.** `GET /api/v1/storage` answers `{ categories, databases }`; `databases` is `[{ key, label, bytes }]` for `core` and `workitems`, with `bytes` null when the database cannot say its size (an external tracker, an unreachable server, a database other than PostgreSQL). Each category is `{ key, label, bytes, incomplete, entries }` with `key` one of `worktrees`, `repository-clones`, `preview-data`, `chat-sessions`, `agent-installs`, `temp`, `backups` (the pre-restore backups ILD keeps) or `other`; `entries` is the breakdown (`{ key, label, repositoryId, repositoryName, bytes, incomplete }`) for worktrees (per repository, `unowned` for what no run owns), repository clones (per repository, `repositoryName` null for a clone whose repository is gone, and `unowned` for the rest of the clone store), preview data (one entry per repository folder under `.preview-volumes`, keyed by the repository id, its label marking a folder whose repository is gone (`repositoryName` null) or has Keep preview data off, and `unowned` for anything else there) and temp (`private`, `agent-read`, `scratch`), plus `shared` for hard-linked files that do not belong to one entry, and the category's `bytes` is the sum of those that were measured. Sizes are allocated bytes, each file counted once however many links it has, and links are never followed; `incomplete` means some of it could not be read — for a category, also that one of its entries was not measured — and `bytes: null` means not measured (a scratch root that is the process temp directory, or a platform other than Linux). No server path is returned. Worktrees exist only for runs in progress or pinned: a run's worktree, local branch and AI session snapshots are removed when it ends, so there is no bulk worktree cleanup. User-only: the agent token gets 403.
- **Run history.** `GET /api/v1/loopruns/{id}` carries `waitingRunNodeId`: the id of the Human node execution a run waits on a person at, null when it is not waiting for one (running, ended or halted), which is the question a human input suggestion must name to be decided; and `historyKeptUntil`: for a Completed or Cancelled run that is not pinned, when it ended plus the `run.retentionDays` in force now; null for a run that has not ended or is pinned. The sweeper deletes the run once that has passed and its work item is Done. `POST /api/v1/loopruns/{id}/cleanup` removes a finished run's worktree, local branch and session snapshots now, pinned or not, and keeps the run.
- **Backup and restore.** User-only, and the agent token gets 403 on every route ([ADR-0029](./adr/0029-backup-and-restore.md)). `{db}` is `core` or `workitems`; anything else is 404. `GET /api/v1/storage/backups` answers `{ databases: { core, workitems }, secretKeyConfigured, minPassphraseLength }`, each database `{ available, reason?, preRestoreBackup?: { createdAt, bytes } }` (`reason` says why `available` is false: PostgreSQL is not the database, or the tracker offers no backup). `POST /api/v1/storage/backups/{db}` with `{ passphrase }` answers the encrypted file (`application/octet-stream`, `ild-{db}-{UTC yyyyMMdd-HHmmss}.ildbackup`); a passphrase shorter than `minPassphraseLength` (12) is 400. `POST /api/v1/storage/backups/{db}/restore` takes multipart fields `file`, `passphrase` and `confirmation` (the word `RESTORE`), in that order, with no size limit, and answers `{ restarting }`: true for `core`, whose restore ends with ILD restarting. A refusal is 400 (no confirmation, no file), 422 (wrong passphrase, a damaged or altered file, a backup of the other database or from a newer ILD, a different `ILD_SECRET_KEY`) or 409 (a loop run, a worktree preview or a chat turn is active, or another backup or restore is in progress), always `{ error }` and always before any data changed. While a restore runs every other `/api` request is 503. `GET /api/v1/storage/backups/{db}/pre-restore` downloads the encrypted backup the last restore took of the data it replaced, or 404. Backup, restore and that download are logged with the username.
- **Preview data.** A repository carries `keepPreviewData` (false by default): `GET /api/v1/repositories` and `GET /api/v1/repositories/{id}` return it, `POST` accepts it and `PUT` changes it only when it is sent, so an absent or null value keeps the stored one. `DELETE /api/v1/storage/preview-data/{repositoryId}` deletes the repository's persisted preview volumes and answers 200; it is what both the storage page and the repository's Reset preview data call, and it also takes the id of a deleted repository. It answers 409 `{ error }` naming the work item while a preview of the repository is running or starting, whatever its setting, and 400 for an id that is not a GUID. A preview start or install of a keep-on repository while another work item's preview of it is running is a 400 `{ error }` (`A preview is already running for work item {id} ({title}). Stop it before starting this one.`), on the user and agent preview endpoints alike. User-only, and no agent endpoint or MCP tool removes preview data.
- **Preview start progress.** While a full preview start runs, `GET .../preview` (and `get_preview`) answers that start's progress, from the moment the request is accepted, instead of the previous view: `state` is `installing` (with `install: { index, total, command }`, the step as written in `ild.config.json`) or `starting`, and each service's `status` moves `pending` → `starting` → `waitingForHealth` → `running`, or `failed` with `exitCode` and `error` as soon as its process exits or its health check times out; `port` is known before the install, the other fields as the service launches. Every change pushes `PreviewStateChanged`. A start that fails waits for every service to settle, stops what it launched and answers 400 as before; `GET .../preview` then keeps `state: failed` with the reason in `message` until the next start or stop. `POST .../preview/start` (user and agent, and `start_preview`) accepts `wait` (default true); `wait: false` answers at once with the in-progress status and continues in the background, and a start already running is not started again.
- **Repository parallelism.** A repository carries `parallelism` (0, meaning unlimited, by default; 0 to 1000): `GET /api/v1/repositories` and `GET /api/v1/repositories/{id}` return it, `POST` accepts it and `PUT` changes it only when it is sent, so an absent or null value keeps the stored one; a value outside 0 to 1000 is a 400 and changes nothing. The scheduler leaves a Ready item of a repository in Ready, untouched, while that many of the repository's items are Running, in Human Feedback or WaitingForIld. The limit is each ILD instance's own setting, but the items it counts are the repository's items on the whole WorkItem Server board, whichever instance runs them. `GET /api/v1/workitems/{id}` and `GET /api/v1/workitems/page` carry `repositoryParallelismHold: { inProgress, limit }` on a Ready item the latest scheduler pass held back that way, and null on every other item; a change to it is announced as a `WorkItemStateChanged` from Ready to Ready. `POST /api/v1/workitems/{id}/start`, from a signed-in user (401 otherwise), starts a Ready item now the way the scheduler would, held or not and whether or not the scheduler is paused: it skips only the repository limit, and leaves the limit as it is. It answers 200 with the item as `GET /api/v1/workitems/{id}` returns it once the item has left Ready (Running, or Human Feedback when no single loop matches its tags or its run fails to start), 404 for an unknown item, and 409 `{ error }`, changing nothing, when the item is not Ready, this instance already runs as many work items as its concurrency cap allows, or ILD is shutting down, and 503 `{ error, detail }` when the WorkItem Server is unreachable. The started item holds a repository slot like any other until it is Done.

A representative slice of the ILD API: `POST /api/v1/auth/login`, `GET /api/v1/workitems`, `POST /api/v1/workitems/{id}/transition`, `POST /api/v1/workitems/{id}/start` (see Repository parallelism), `GET /api/v1/loopruns/{id}/events`. Controllers live under `ILD.Api/Controllers`; consult them for the exhaustive route list rather than duplicating it here.

## Realtime channel

Two SignalR hubs broadcast state changes, both emitting `{ type, payload, timestamp }`:

- `/hubs/loop-run` — run-level events
- `/hubs/work-item` — work-item-level events, plus the instance-wide settings events (`SchedulerStateChanged`, and the network filter's `NetworkPolicyChanged`, `NetworkLogAppended`, `NetworkLogCleared`)

Event payload types are statically modelled in `frontend/src/types/signalr.ts`. See [Architecture → Realtime channel](./architecture.md#realtime-channel) for the event catalogue.

## WorkItem Server API

The standalone server owns work-item state and claim semantics (see [ADR-0001](./adr/0001-standalone-workitem-server.md)). Its surface centres on listing and polling work items (`GET /workitems`, `GET /workitems/poll` for heartbeat + ready-item polling) and atomic state changes (`POST /workitems/{id}/transition` for claim-or-permissive transitions). Every request that can change a work item — any `POST`, `PUT` or `DELETE`, and `GET /workitems/poll` — names who it acts for in `X-ILD-Actor`, base64 of UTF-8 JSON `{ username, kind, detail?, workItemId? }` (`username` non-blank, at most 256 characters; `kind` one of `Human`, `Agent`, `Chat`, `System`; `detail`, at most 1024 characters, required for every kind but `Human`), and is a 400 `{ error }` without a usable one, before anything is written. The server records it on the history it keeps of every change to a tracked field, which `GET /workitems/{id}/history` answers in the shape of the ILD route above, deleted items included; a transition takes an optional `reason` for its status entry. History rows are never changed or deleted, not even with their item. It keeps no conversation: a run's conversation lives in that run's event log on the ILD instance. `GET /health` reports liveness.

### Backup endpoints (outside the contract)

The built-in server also serves `GET /maintenance/backup` (`{ version, migrations, databaseBytes }`), `POST /maintenance/backup/export` (the database as an unencrypted archive) and `POST /maintenance/backup/import` (a raw `application/octet-stream` body, no size limit), behind the same API key; the POSTs name the actor in `X-ILD-Actor`. They are **not** part of the work item contract an external tracker implements ([ADR-0025](./adr/0025-workitem-server-contract-is-tracker-mappable.md)): a tracker without them answers 404 and ILD reports the work item backup as unavailable. An import replaces all data, migrates forward, and sets the heartbeat of every Running or WaitingForIld item to the import time. See [ADR-0029](./adr/0029-backup-and-restore.md).
