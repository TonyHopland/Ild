# ADR-0035: A run gets its repository's toolchains and ILD's agents from a shared, read-only store

> **Status: amended by [ADR-0036](./0036-runs-always-in-containers.md).** The ILD image is slim and `ild-runner-full` is no longer built; runs always get their toolchains from the store, or from a runner image of the operator's own with `ILD_RUN_TOOLCHAINS=off`.

[ADR-0033](./0033-kubernetes-run-host.md) and [ADR-0034](./0034-container-run-host.md) ran every loop run under one runner image: the ILD image's toolchains (Node, the .NET SDK, Chrome), plus three coding agents baked in at whatever version was newest when it was built. A node project carried a .NET SDK, a repository that needed Python or Go had no way to get it, Codex and Copilot were missing, and a run's agent was not the version ILD showed in Settings, with no update cooldown. Taking the model from [devvm](https://github.com/devvmhq/devvm), a run now starts from a slim image and gets the toolchains its repository needs, and the agents ILD has installed, from a store every run mounts read-only.

## Decision

- **The runner image is slim.** `ild-runner` is Ubuntu with what every project uses (git, a shell, a compiler, curl, jq, ripgrep), Chrome for the chrome-devtools MCP server (it needs system libraries a store cannot give), and [mise](https://mise.jdx.dev). It carries no language toolchain and no agent. The MCP server in it is a self-contained build, started through its apphost at the path the agent's MCP config names, so it runs whatever .NET the project has, or none. Adapters start the server through its apphost on every host, so the config is the same everywhere.
- **Toolchains are installed once per version, into a store.** The store is named volumes (`ild-tools-agents` and the others below) on a single engine, and a ReadWriteMany claim (`ILD_K8S_TOOLS_CLAIM`) on Kubernetes. ILD fills it by running a script, as the runner's user, in a short-lived installer of the runner image that mounts it writable. mise installs each toolchain; the script records its `PATH` entries and variables (`DOTNET_ROOT`) in a manifest. A later run that needs the same reads the manifest, and runs never run mise or download a toolchain themselves.
- **Agents come from ILD's own installs.** The store gets every agent ILD has a current install of, at that install's version, so a run uses what Settings shows, rollbacks and the update cooldown included. Each agent gets a wrapper that starts it on a Node of its own (the newest LTS line), so a project that pins an old Node cannot break its agent, and the agent's own commands still see the project's Node.
- **What a run needs is read from the repository, not from the branch the agent writes.** ILD reads its own checkout of the base branch before the run exists. `ild.config.json`'s `run.tools` names tools outright and wins; otherwise a project's `mise.toml` or `.tool-versions`; otherwise marker files with their version files (`package.json` and `.nvmrc`, a .NET project's target framework or `global.json`, `.python-version`, `go.mod`, `rust-toolchain.toml`), at the top of the repository or one or two folders down. Tool names and versions are refused if they could carry a shell character.
- **A .NET SDK comes with the Azure Artifacts credential provider.** From SDK 9.0.200 on, NuGet finds `nuget-plugin-*` commands on `PATH`; the store installs the pinned provider tool once per SDK version and puts it on that toolchain's `PATH`, so a run restores from a private feed with the endpoints ILD hands it. An older SDK gets none.
- **A run's home is where it installs things.** The store is read-only, so `NPM_CONFIG_PREFIX` is the run's `$HOME/.local` and its `bin` is on `PATH`, after the toolchains and agents. When the run's Node has corepack, its shims go there too, so `pnpm` and `yarn` are what the project's `packageManager` pins. ILD's own `PATH` never reaches a run.
- **Off is a setting.** `ILD_RUN_TOOLCHAINS=off` gives runs only what their image has, for a runner image of the operator's own. A Kubernetes cluster without a ReadWriteMany claim for the store gets the same, with a warning at startup.

- **The store has three zones, and a repository cannot write what other repositories run.** A repository chooses its tools (`mise.toml`, `.tool-versions`, `run.tools`), and a mise backend or a registry short name (`npm:prettier`, `cargo:x`, `pipx:x`, `prettier`, which mise resolves to npm) installs a package whose install scripts run: `postinstall`, `build.rs`, an sdist build. If that wrote into the one store, it could replace a shared Node or an agent CLI's wrapper, and every later run of every repository, holding gateway and ILD API tokens, would execute it. So an installer mounts only the zone it writes:
  1. **Agents** (`/opt/ild-tools`; volume `ild-tools-agents`; claim `subPath` `ild`): the agents' Node and the agent CLIs, written only for ILD's own picks.
  2. **Toolchains** (`/opt/ild-toolchains`; volume `ild-tools-toolchains`; `subPath` `toolchains`): the 13 mise core tools by plain name (`bun`, `deno`, `dotnet`, `elixir`, `erlang`, `go`, `java`, `node`, `python`, `ruby`, `rust`, `swift`, `zig`), with their own mise data directory, cache and manifests. Every repository shares it. It is safe to share because a core tool is installed from its upstream's own release and runs no code a repository chose: the repository picks only a name and a version, which the existing pattern limits to characters a shell cannot use.
  3. **Repository tools** (`/opt/ild-repo-tools`; volume `ild-tools-repo-<repository id>`; `subPath` `repo-tools/<repository id>`): every other spec. Its installer mounts only that repository's volume writable, plus the toolchains zone read-only with the repository's core tools on `PATH`, so `npm:`, `pipx:` and `cargo:` find their runtimes. A run mounts every zone it has something in, read-only, and only its own repository's; a Kubernetes pod never mounts the claim's root. Inside a repository's volume each set of non-core specs has a folder named for a hash of the sorted specs, so a changed set installs into a fresh folder. (The mount path is the same for every repository, rather than containing its id, because a container mounts only one and an empty volume takes its ownership from the image's directory at the mount point.)

  The install script runs once per zone with `ILD_TOOLS_ROOT` set to the zone (or the folder in it), and a run reads each zone's manifests exactly as before; only the paths a manifest may name differ, and the output of a zone's installer is accepted only for paths under that zone. On Kubernetes the installer pod first runs a fixed `mkdir` of ILD's own, in an init container that mounts the claim, so the `subPath` exists with the runner's ownership; the container that installs mounts only its `subPath`.

- **Backends stay allowed.** Refusing `npm:` and the like would break repositories that pin a formatter or a CLI for mise, and an allowlist of core names would not stop `prettier`, which mise resolves to npm anyway. They are installed, apart from the shared zones.
- **Install scripts are off where a repository could not be the only victim.** The agents and toolchains installers set `npm_config_ignore_scripts=true`; the agents zone's own npm call passes `--ignore-scripts=false` with its `allowScripts` list, so an agent's own install script still runs. A repository's own zone runs scripts, since many tools need them, unless the repository sets `run.ignoreScripts: true` in `ild.config.json`.
- **Chats get the agents and toolchains zones only.** All chats share one container, so a repository's own zone has no place in it. A chat skips non-core tools, and ILD logs each one.

## Considered options

- **Image variants per stack** (`ild-runner-node`, `ild-runner-dotnet`): quick, and no store, but every combination is an image to build and publish, the agents stay baked in at a version ILD does not choose, and a version pin in a repository still could not be honoured.
- **Installing in each run**: no shared state, but every run downloads its toolchains again, and the run's network, which reaches only ILD, would have to reach the internet.
- **A downloader of ILD's own** for each toolchain: no new tool, but it re-implements what mise already does for every language, and projects that already pin tools for mise would get a different answer.
- **Building an image per repository** with the engine's build API: fast runs once built, but Kubernetes cannot build, and every new pin is a new image to store.

## Consequences

- The first run of a repository waits for its toolchains to download; later runs and other repositories on the same versions do not. The store grows with every version used and is never pruned by ILD; remove the volume, or the claim's contents, to start it over.
- The installer's network reaches only ILD, as a run's does, and it downloads through the egress proxy: an `internal` network of its own on Docker and Podman, and a NetworkPolicy of its own on Kubernetes that allows egress only to ILD's pod on the proxy port, with no DNS. A namespace that denies egress by default needs no rule for pods labelled `ild/role=tools`, but the ingress rule for ILD's pod must admit them on the proxy port, as `docs/kubernetes/ild-ingress-networkpolicy.yaml` does for every pod labelled `app.kubernetes.io/managed-by=ild`.
- A repository's own tools are installed again for each change to its set of non-core specs, and a store that held tools in the one earlier volume installs everything once more into the zones; the old contents are unused. That holds on a single engine because the agents' zone is a new volume, `ild-tools-agents`, not the old `ild-tools`: what an install script could have written there before the zones is never mounted or reused, so a store that was already tampered with does not carry over.
- **Accepted risk: a malicious spec that is merged poisons its own repository.** A tool's install script in the repository's zone can write anything that repository's later runs execute, including through the agent's `PATH`. The zone limits it to that repository's runs, and the folder's hash and ILD reading specs from the base branch (never the agent's branch) mean a spec has to be merged first. A repository that does not want this sets `run.ignoreScripts`.
- **Fork pull requests do not apply.** ILD runs only branches it creates in the repository, so a contributor's fork never supplies specs to a run.
- **Accepted risk: a compromised upstream core installer** (a release of `node`, `python` and the others, or mise itself) writes to the shared zone. That is the supply chain ILD already trusts for every toolchain.
- **Installer traffic is judged by the operator's policy, under a scope of its own.** An installer's proxy credential is a token ILD signed for its zone (`agents`, `toolchains` or `repo-<repository id>`, [ADR-0019](./0019-agent-egress-through-in-container-proxy.md)), and the Network Log records the zone. Install scripts fetch from hosts nobody can list in advance (esbuild, Playwright, Prisma and sharp download binaries), so ILD ships no fixed allowlist: it seeds the **Installers** scope of the whitelist once with the hosts mise, npm, pip, cargo and the NuGet credential provider use, and the operator edits it in Settings → Network like any other list. In `whitelist` mode an installer is allowed what that scope and the global list allow; in `blacklist` mode what neither blocks; `monitor` allows everything and logs it. A failed install names the hosts the proxy refused it. The scope is one for all installers, not per zone or repository. The proxy variables are the same as an agent's, so what honours them for agents (mise, npm, pip, cargo and the credential provider's `dotnet tool install` all read `HTTPS_PROXY`) honours them for installers; a tool that ignores them has no other route and fails.
- System packages a project needs beyond the slim image (a database client, a second browser) are a runner image of the operator's own, `FROM ild-runner`.
