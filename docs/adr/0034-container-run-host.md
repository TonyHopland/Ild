# ADR-0034: A loop run can be a container, with a volume and a network, swept by label

[ADR-0032](./0032-run-host-interface.md) put where a run lives behind `IRunHost`, and [ADR-0033](./0033-kubernetes-run-host.md) built the pod host. `ILD_RUN_HOST=container` is the single-machine version: each loop run gets a container of its own through the Docker-compatible REST API. It does not spread load, but it isolates a run from ILD and from other runs the same way.

## Decision

- **One implementation for Docker and Podman**, over the `/v1.41` endpoints that Podman's compatibility service also serves, on a unix socket. A small hand-written client does the REST calls with `HttpClient` and opens the exec stream on a connection of its own: the engine hijacks it (a `101` from Docker, a `200` from Podman), frames stdout and stderr with an eight byte header (a terminal is raw), and stdin ends when ILD half-closes the socket. The exit code is read from the exec afterwards; a stream that ends with the command still running is a dropped connection and fails the node.
- **The shared part is a base class.** `ExecRunHost` holds everything that does not depend on the transport: commands as process groups recorded under a name so they can be killed before a retry, files, bundles, the terminal, the scrubbed environment and the staging of the files a launch reads. A host supplies an exec stream and the lifecycle. The pod host keeps only the pod code. A routing host sends a call to the run's environment by the path it names (`/ild-run/<run id>`, the same in both) and everything else stays local.
- **Opt-in, and the socket is a trust decision.** `local` stays the default, so a local install never needs a socket. `ILD_CONTAINER_SOCKET` is required and never detected, because whoever holds the socket controls every container on the host. Rootless Podman, where the socket is the user's own account, is the supported setup; a rootful socket is root-equivalent on the host. ILD asks the engine whether it is rootless (Podman's `/libpod/info`, else Docker's `/info`) and shows a warning in settings when it is not. When the engine answers but does not say, it shows nothing rather than guess; the documentation carries the warning then. When ILD cannot reach the engine at all it says so too, since no run can start. ILD's entrypoint, not the operator, gives ILD's user (never the agent's) a group that can open the mounted socket, because the drop from root rebuilds that user's groups and a `group_add` is lost.
- **A run is three objects**, made in this order at Start: a named volume, an `internal` network, the container (the runner image under `tini`, uid 10001, all capabilities dropped, `no-new-privileges`, the CPU and memory limits shared with the pod host). The container stays up while a Human node waits. The preview target is the container's address on its network.
- **The network reaches only ILD when ILD runs in a container.** The container is given ILD's host name from `ILD_API_URL` as an address of its own network. With ILD in a container, that is ILD's container, connected to the network, and the run reaches ILD and nothing else. With ILD on the host it is the network's gateway, which is the host itself: traffic to it is handled by the host's input rules, not the `internal` network's forwarding block, so the run can reach **every service listening on the host**, and the egress proxy, which has to listen on all interfaces for the run to reach it, accepts connections from the whole LAN. Nothing in ILD closes that; a host firewall limiting the run networks to ILD's port and the proxy port does, and ILD in a container is the setup that isolates. Binding the proxy to the run networks' gateways instead was left out: the networks are made per run, after ILD has started.
- **Cleanup is explicit, then swept.** There are no owner references on one host, so ending a run deletes the container, then the volume, then the network (ILD leaves it first), ignoring what is already gone. The objects carry the labels of the pod host (`app.kubernetes.io/managed-by=ild`, `ild/instance`, `ild/run`) and the one sweeper serves both hosts: at startup and on a timer it deletes the objects of runs that are finished or gone and keeps those of runs that can still be retried. It only touches its own instance. A killed ILD leaves nothing behind after its next start.
- **The runner image owns `/ild-run`**, and the volume is mounted there, so it starts out writable by the runner: a named volume takes the ownership of the image directory it covers.

## Considered options

- **Detecting the socket** (`/var/run/docker.sock`, the user's Podman socket). Rejected: it picks the trust level for the operator.
- **A Docker client library.** Rejected: the surface used is a dozen calls and one hijacked stream, and a library's version of the API would have to match both engines.
- **A pod-like grouping of one container with a sidecar for the network.** Rejected: an internal network per run reaches the same isolation with nothing to run beside the container.
- **Publishing a port per preview on the host.** Rejected: the preview proxy already forwards to an address, and the pod host works the same way.
