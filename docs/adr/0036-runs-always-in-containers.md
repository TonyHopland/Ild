# ADR-0036: ILD from its image always runs agents in containers; local runs are for `dotnet run` only

[ADR-0032](./0032-run-host-interface.md) put where a run lives behind `IRunHost`, with `local` as the default and `ILD_RUN_HOST` choosing `container` ([ADR-0034](./0034-container-run-host.md)) or `kubernetes` ([ADR-0033](./0033-kubernetes-run-host.md)). Chats and the provider sign-in have since moved into containers and pods too. That left two complete ways of containing an agent: a container of its own, and a second Linux user inside ILD's container ([ADR-0014](./0014-agent-uid-isolation.md)), with its own preview rules ([ADR-0016](./0016-preview-runs-as-the-agent.md)), its own firewall ([ADR-0019](./0019-agent-egress-through-in-container-proxy.md)), shared groups, ambient capabilities and `NET_ADMIN`. Every change to how an agent starts had to be made, and tested, twice. ILD now has one way of containing an agent, the container.

## Decision

- **The run host is not a setting.** `ILD_RUN_HOST` is gone. ILD started from its image (which sets `ILD_IMAGE=1`) runs every loop run, chat and provider sign-in in a container of its own, or in a pod when the image runs in a Kubernetes cluster (`KUBERNETES_SERVICE_HOST` is set). ILD started any other way, which is `dotnet run` by a developer or by a preview of ILD's own repository, runs them as its own processes.
- **`local` is for development only.** It runs the agent as ILD's own user, with no second user and no firewall, and with no egress proxy unless `ILD_NETWORK_PROXY_PORT` is set (then only the agents that honour `HTTP_PROXY` go through it). It is not a way to deploy ILD.
- **The agent uid split is removed.** The image has one user, `ild`. The entrypoint no longer creates shared groups, agent-readable directories, firewall rules or ambient capabilities, and drops to `ild` with `gosu`. Compose no longer grants `NET_ADMIN`. On the first start after an upgrade, the entrypoint gives ILD back the files the agent user left in `/data` and `/worktrees`.
- **ILD's image is slim.** It has no .NET SDK, Chrome or second user; it keeps git, and Node with npm, which install the coding agents ILD hands to runs ([ADR-0035](./0035-run-toolchains.md)). `WITH_NODE`, `WITH_DOTNET_SDK` and `WITH_CHROME` are gone. `ild-runner-full` is no longer built: runs get their toolchains from the store, and a Kubernetes cluster needs a ReadWriteMany claim for it (`ILD_K8S_TOOLS_CLAIM`), or a runner image of the operator's own with `ILD_RUN_TOOLCHAINS=off`.
- **Compose is the container setup.** `docker-compose.yml` mounts the engine's socket, named by `ILD_CONTAINER_SOCKET_HOST` (it refuses to start without it), and builds the runner image. The separate `docker-compose.container-runs.yml` overlay is gone.

## Considered options

- **Keep `local` as an option for deployments without an engine.** It keeps ILD runnable where no socket or cluster can be given to it, but it is the second containment model this decision removes, with its firewall, groups and capabilities, and the agents in it share ILD's kernel namespace and network.
- **Keep the setting but default it to `container`.** One fewer surprise for an operator who reads the docs, but it leaves every code path in place and a setting whose only safe value is the default.
- **Detect any container, not ILD's image.** A preview of ILD's own repository runs `dotnet run` inside a run's container, where it must run its agents locally; only ILD's image says that ILD is deployed.

## Consequences

- Every deployment needs a container engine socket or a Kubernetes cluster. Compose needs `ILD_CONTAINER_SOCKET_HOST` in `.env`. A rootful engine's socket is root-equivalent, as [ADR-0034](./0034-container-run-host.md) says.
- A run is isolated from ILD, its database and its secrets by a container boundary rather than by a uid, and the egress limits are enforced by the run's network, which reaches only ILD.
- ADR-0014, ADR-0016 and the firewall of ADR-0019 describe the earlier design. The egress proxy, its lists and its log remain.
- Developing ILD with `dotnet run` runs agents unconfined, as before when `AGENT_USER` was empty.

## The egress proxy's destination rules

The proxy is the only way out of a run's network, and it listens where the run can reach it, so it must not become a way into ILD. Five rules follow, decided by the **addresses the proxy resolved** (it resolves a name once and dials what it resolved), never by the name asked for:

- **Loopback is always refused**, for an agent's connection and for a forward alike, in every mode and whatever the lists say: `127.0.0.0/8`, `::1`, IPv4-mapped loopback, `0.0.0.0` and `::`. ILD's loopback holds its forward listeners, its preview listeners and the gateway's HTTPS listener. The `*.preview.ild` hand-off is the one thing that reaches ILD's web port, and it sends the preview host as `Host` so it reaches no other route.
- **Protected destinations are on by default and the operator can switch each off** (`network.protect.<id>`, app state like the mode and lists, applied on the next connection): ILD's own addresses, ILD's database, the WorkItem Server and, on Kubernetes, the Kubernetes API. While one is on, a connection whose resolved addresses match it is refused in every proxied mode and a whitelist entry does not override it. The log records the refusal with its reason, not as a list decision.
- **A declared forward ([ADR-0020](./0020-raw-tcp-egress-through-declared-forwards.md)) is exempt from the protected destinations**, not from the loopback rule: declaring it is an operator decision, and it is still judged by the mode and lists. A forward to ILD's own database server exposes that server to every agent, so the credential and the database it lets in are the operator's to scope.
- **Other runs' networks are always refused**, like loopback: not switchable and not exempted by a forward. The proxy is on every run's network, so without this a run could ask it to `CONNECT` to another run's address and reach that run's dev server or preview. With container runs it is the whole subnet pool (`ILD_CONTAINER_SUBNET_POOL`, one /28 per run, chat and installer); with Kubernetes, which has no network of its own per run, it is the IP of every pod ILD made, read from the cluster and cached with the protected destinations (30 s), so a pod younger than that may not be covered yet.
- **Link-local and cloud metadata addresses are a protected destination, on by default** (`network.protect.link-local`, switchable like the others, exempt for a declared forward): `169.254.0.0/16`, `fe80::/10` and AWS's IPv6 metadata address `fd00:ec2::254`. [ADR-0019](./0019-agent-egress-through-in-container-proxy.md) left these to `whitelist`, which made the cloud credentials of the machine ILD runs on one `CONNECT` away in the default `monitor` mode. Other private addresses (the LAN) are still judged by the mode and lists alone.

The proxy also needs a launch's own signed credential to be used at all, and binds no wider than it must (ADR-0019).

ILD itself is not reached through the proxy: ILD's host is on `NO_PROXY` in a run's environment, so the gateway and the MCP endpoint go direct over the run's network, which allows exactly that.

The removed uid firewall also dropped DNS. Run and chat environments now have no working DNS (an engine's `Dns` is `127.0.0.1`; a pod has `dnsPolicy: None` and no DNS egress rule), ILD's name comes from the container's hosts file or the pod's `hostAliases`, and the proxy alone resolves names. A run or chat in network mode `off` has DNS back for as long as it has the direct route below.

**Network mode `off` gives the run a direct route, as [ADR-0019](./0019-agent-egress-through-in-container-proxy.md) defines it.** A run's or chat's network reaches only ILD, so a proxy that carries only HTTP and `CONNECT` left SSH, UDP and raw TCP with no route even in `off`. While a launch is in `off`, the run's container is connected to a second, non-internal network made by ILD (`ild-open-<instance>`), and the run's or chat's pod gets a second NetworkPolicy that allows all egress (a CNI that enforces NetworkPolicy is needed, as ever, and an operator's namespace-wide default-deny egress policy still applies). The launch gets no proxy variables. The route is per container or pod, not per process; a launch in a proxied mode removes it only when no process launched in `off` is still running in that run; chats share one container, so one chat in `off` opens it for all. The protected destinations do not apply to a direct connection.

**Enforced is observed, not asserted.** A probe tries a direct connection out of an environment to an address ILD itself reaches; the status is `enforced` only once that failed, `advisory` when it connected and `unverified` before any probe has run.
